# Human Request Layer 설계 참고사항

현재 v1에서는 **Human이 이미 실행 목표를 확정한 상태**만 다룬다.

```
Human
↓
GoalSpec
↓
Planning
↓
TaskContract
↓
Execution
```

예:

```
"모바일 프로젝트 캐러셀의 애니메이션 떨림을 개선한다"
"사용자 조회 로직을 리팩토링한다"
"예약 페이지에 필터 기능을 추가한다"
```

이런 요청은 Human이 원하는 결과가 이미 명확하기 때문에 바로 `GoalSpec`으로 표현할 수 있다.

하지만 실제 개발 과정에서 Human은 항상 명확한 Goal을 가지고 AI를 사용하는 것은 아니다.

예를 들어:

```
"여기 구조 좀 이상하지 않아?"
"이 컴포넌트 리팩토링해야 할 것 같은데 어떻게 생각해?"
"이 코드에서 문제될 만한 부분 있어?"
"성능이 안 좋은 것 같은데 어디부터 봐야 할까?"
"이 PR 이 정도면 충분해?"
"이 코드 왜 이렇게 작성된 거야?"
"A 방식이랑 B 방식 중 뭐가 나아?"
"이 Repository에서 개선할 만한 곳 찾아봐"
```

이런 요청들은 모두 성격이 다르며, 곧바로 `GoalSpec`으로 변환해서는 안 된다.

---

# 1. 문제

예를 들어 Human이 다음과 같이 질문했다고 하자.

```
Human:
"이거 리팩토링 필요하지 않을까?"
```

이를 곧바로:

```
GoalSpec
objective: "이 컴포넌트를 리팩토링한다"
```

로 변환하면 AI가 Human보다 먼저 실행 방향을 확정하게 된다.

하지만 Human의 실제 의도는:

```
"정말 리팩토링이 필요한지 먼저 판단해줘"
```

일 수도 있다.

즉:

```
판단 요청
≠
실행 요청
```

이다.

따라서 장기적으로는 `GoalSpec`보다 상위에서 **Human Request의 의도(Intent)를 먼저 해석하는 계층**이 필요하다.

---

# 2. Human Request Layer

장기 구조는 다음과 같이 확장할 수 있다.

```
Human Request
      │
      ▼
Intent Analysis
      │
      ├── Execute
      ├── Investigate
      ├── Review
      ├── Explain
      ├── Decide
      └── Discover
```

핵심은:

> Human의 모든 요청이 Goal은 아니다.

라는 점이다.

`GoalSpec`은 이 중 **실행하기로 확정된 목표**를 표현하는 Contract로 둔다.

---

# 3. Request Intent

## 3.1 Execute

Human이 이미 원하는 결과를 알고 있는 경우다.

예:

```
"이 컴포넌트를 분리해줘"
"로그인 버그를 수정해줘"
"모바일 애니메이션을 개선해줘"
```

흐름:

```
Human Request
↓
Execute Intent
↓
GoalSpec
↓
Planning
↓
TaskContract
↓
Execution
↓
Verification
```

현재 v1이 우선 해결하려는 영역이다.

---

## 3.2 Investigate

Human이 실행보다 **분석과 판단을 먼저 원하는 경우**다.

예:

```
"여기 리팩토링 필요해 보여?"
"이 구조 문제 있어?"
"왜 렌더링이 느린 것 같아?"
```

흐름:

```
Human Request
↓
Investigate Intent
↓
Repository Investigation
↓
Findings
↓
Recommendation
↓
Human Decision
```

Human이 이후:

```
"그럼 그렇게 수정해줘"
```

라고 승인하면 그 시점에:

```
GoalSpec
↓
Planning
↓
TaskContract
```

로 전환한다.

중요한 점은:

> Investigation이 자동으로 Execution으로 이어지지 않는다.

는 것이다.

---

## 3.3 Review

이미 만들어진 결과물이 기준을 만족하는지 검증하는 요청이다.

예:

```
"이 PR 괜찮아?"
"이 구현 이 정도면 충분해?"
"이 변경사항 제대로 된 거 맞아?"
```

흐름:

```
Artifact / Diff / PR
+
Review Criteria
↓
Review
↓
Findings
↓
Pass / Concern / Fail
```

`Investigate`와 비슷하지만 목적이 다르다.

```
Investigate
= 무엇이 문제인지 찾는다

Review
= 이미 만들어진 결과가 기준을 만족하는지 검사한다
```

---

## 3.4 Explain

코드를 수정하거나 평가하는 것이 아니라 **이해하기 위한 요청**이다.

예:

```
"이 함수 왜 이렇게 작성된 거야?"
"이 worktree 로직이 어떻게 동작해?"
"왜 여기서 rmSync를 호출하는 거야?"
```

흐름:

```
Human Request
↓
Explain Intent
↓
Relevant Context
↓
Explanation
```

이 경우 결과는 코드 변경이 아니라 Human의 이해다.

---

## 3.5 Decide

여러 선택지 사이의 trade-off를 비교하고 판단을 요청하는 경우다.

예:

```
"이걸 model 폴더에 둘까 그냥 planning 바로 아래에 둘까?"
"Context를 하나로 합치는 게 나아, 분리하는 게 나아?"
"A 방식이랑 B 방식 중 뭐가 더 적절해?"
```

흐름:

```
Human Request
↓
Decide Intent
↓
Options
↓
Trade-off Analysis
↓
Recommendation
↓
Human Decision
```

중요한 것은 AI가 단순 선호를 말하는 것이 아니라:

```
선택지
+
Repository Context
+
Constraints
+
Trade-off
```

를 근거로 판단해야 한다는 점이다.

---

## 3.6 Discover

Human이 특정 문제를 지정하지 않고 **AI에게 개선할 가치가 있는 문제 자체를 찾아달라고 하는 경우**다.

예:

```
"이 Repository에서 개선할 곳 찾아봐"
"구조적으로 위험한 부분 있어?"
"지금 가장 먼저 손볼 만한 곳이 어디야?"
```

흐름:

```
Repository
↓
Discovery
↓
Candidate Issues
↓
Impact / Risk / Cost 평가
↓
Prioritized Opportunities
```

예:

```
1. ProjectsCarousel animation coupling
2. API error handling duplication
3. test coverage gap
4. outdated dependency
```

`Goal-based` 방식보다 한 단계 상위의 기능이다.

```
Goal-based
= Human이 무엇을 할지 결정

Discovery-based
= AI가 무엇을 할 가치가 있는지도 탐색
```

---

# 4. Skill과 Intent는 다르다

이 기능들을 `Skill` 자체로 보는 것은 적절하지 않다.

`Intent`는:

> Human이 무엇을 원하는가

이고,

`Skill`은:

> 그 요청을 해결하기 위해 AI가 어떤 전문적인 방법을 사용할 것인가

다.

예:

```
Skills
├── refactoring-review
├── architecture-review
├── performance-investigation
├── accessibility-review
├── dependency-audit
└── test-quality-review
```

Human이:

```
"이 컴포넌트 리팩토링 필요해?"
```

라고 요청하면:

```
Human Request
↓
Investigate Intent
↓
refactoring-review Skill
↓
Repository Analysis
↓
Findings
↓
Recommendation
```

처럼 동작할 수 있다.

즉 역할은 다음과 같이 분리된다.

```
Human Request
= Human이 무엇을 원하는가

Intent
= 요청을 어떤 종류의 작업으로 해석했는가

Skill
= 그 요청을 어떤 전문적인 방법으로 해결할 것인가

GoalSpec
= 실행하기로 확정된 목표

TaskContract
= 실행 가능한 작업 계약
```

---

# 5. Context Target

Request Intent와 별개로 **Human이 무엇을 대상으로 요청했는가**도 중요하다.

예:

```
"이 파일 봐봐"
"이 함수만 설명해줘"
"이 PR 리뷰해줘"
"Repository 전체 구조를 봐줘"
```

장기적으로 다음과 같은 개념을 둘 수 있다.

```
type ContextTarget =
  | { type: "repository" }
  | { type: "directory"; path: string }
  | { type: "file"; path: string }
  | { type: "diff" }
  | { type: "pull-request"; id: string };
```

이를 통해 AI가 항상 Repository 전체를 조사하는 것이 아니라 필요한 범위만 읽도록 만들 수 있다.

---

# 6. Authority Level

또 하나 중요한 것은:

> AI가 어디까지 행동할 수 있는가

이다.

같은 Repository를 보더라도 요청에 따라 권한은 달라야 한다.

예:

```
observe
= 읽고 분석만 가능

propose
= 해결책 제안 가능

plan
= TaskContract 생성 가능

execute
= 코드 수정 가능

commit
= Git commit 가능

merge
= Merge 가능
```

예를 들어:

```
"여기 구조 이상하지 않아?"
```

는 기본적으로:

```
observe
+
propose
```

정도의 권한이면 충분하다.

반면:

```
"그 방향으로 수정해줘"
```

라고 하면:

```
execute
```

까지 올라갈 수 있다.

즉:

```
Question
≠
Permission to modify
```

라는 원칙을 명시적으로 가져가는 것이 중요하다.

---

# 7. Evidence Requirement

AI의 판단은 가능한 한 Repository 근거에 기반해야 한다.

잘못된 예:

```
"이 구조는 좋지 않습니다."
```

더 나은 형태:

```
- 하나의 파일에 API 호출, 상태 관리, UI rendering이 함께 존재한다.
- 동일한 에러 처리 로직이 여러 위치에 중복되어 있다.
- 해당 컴포넌트가 여러 도메인 책임을 동시에 가진다.

따라서 책임 분리를 고려할 가치가 있다.
```

즉 기본 원칙은:

```
Claim
↓
Evidence
↓
Conclusion
```

이다.

특히 다음 Intent에서는 Evidence가 중요하다.

```
Investigate
Review
Decide
Discover
```

장기적으로는 모든 판단 결과에:

```
finding
evidence
reasoning
recommendation
```

같은 구조를 줄 수도 있다.

---

# 8. Investigation과 Execution 경계

Investigation 단계는 기본적으로 Read-only로 둔다.

```
Allowed

- read files
- list files
- inspect repository
- inspect package.json
- inspect dependencies
- inspect git metadata
- analyze architecture
- inspect diff
```

```
Forbidden

- write files
- delete files
- git checkout
- git commit
- git reset
- dependency install
- code modification
- Worker execution
```

즉:

```
Investigation
= 관찰 / 분석 / 판단

Execution
= Repository state 변경
```

으로 명확하게 분리한다.

---

# 9. Human Approval

장기적으로 Human Approval은 Investigation과 Execution 사이의 중요한 경계가 된다.

예:

```
Human:
"이 컴포넌트 리팩토링 해야 할까?"

↓

Investigation

↓

Recommendation:
"animation state와 rendering 책임이 섞여 있습니다.
전체 구조를 다시 만드는 것보다 animation controller만
먼저 분리하는 것이 적절해 보입니다."

↓

Human:
"응 그렇게 해줘."

↓

GoalSpec
↓
Planning
↓
TaskContract
↓
Execution
```

즉:

```
판단
↓
제안
↓
Human 승인
↓
실행
```

의 구조다.

이는 Harness의 Human-in-the-loop 원칙과도 맞는다.

---

# 10. 장기 구조

최종적으로는 다음과 같은 형태를 생각할 수 있다.

```
Human Request
      │
      ▼
Intent Analysis
      │
      ├── Execute ───────────────→ GoalSpec
      │                              │
      │                              ▼
      │                           Planning
      │                              │
      │                              ▼
      │                         TaskContract
      │                              │
      │                              ▼
      │                           Execution
      │
      ├── Investigate ───────→ Findings
      │                           │
      │                           ▼
      │                     Recommendation
      │                           │
      │                           ▼
      │                     Human Approval
      │                           │
      │                           └────→ GoalSpec
      │
      ├── Review ───────────→ Review Result
      │
      ├── Explain ──────────→ Explanation
      │
      ├── Decide ───────────→ Recommendation
      │
      └── Discover ─────────→ Opportunities
                                  │
                                  ▼
                             Human Decision
                                  │
                                  └────→ GoalSpec
```

`GoalSpec`은 시스템 전체의 최초 입력이 아니라:

> **Human과 AI가 실행하기로 합의한 시점의 실행 목표 Contract**

로 보는 것이 더 정확하다.

---

# 11. 현재 v1 범위

이 구조를 지금 전부 구현하지는 않는다.

현재 v1에서는 우선:

```
Human
↓
GoalSpec
↓
RepositoryContext
↓
RelevantContext
↓
Planner
↓
TaskContract
↓
Execution
```

이라는 **Goal → Execution 폐쇄 루프**를 완성한다.

즉 v1의 핵심 질문은:

> 주어진 Goal을 Repository에 근거해서 어떻게 안전한 TaskContract로 변환할 것인가?

이다.

이것이 안정적으로 동작한 뒤 상위에 Human Request Layer를 추가한다.

---

# 12. 이후 확장 순서 후보

현재 구조가 완성된 이후에는 다음 순서가 자연스럽다.

```
v1
Goal → TaskContract → Execution

↓

Next
Investigation / Review
읽고 판단하지만 수정하지 않는 흐름

↓

Next
Human Request + Intent Analysis
요청 종류에 따라 흐름 선택

↓

Next
Skills
각 Intent를 수행하기 위한 전문 분석 절차

↓

Next
Discover
AI가 개선 기회 자체를 탐색

↓

Next
Authority / Approval / Governance
Agent가 어디까지 자율적으로 행동할 수 있는지 관리
```

처음부터 모든 Intent와 Skill을 구현하는 것보다, 실제 사용 과정에서 필요한 책임을 하나씩 추가한다.

---

# 핵심 정리

```
Human Request
= Human의 자연어 요청

Intent
= 요청이 어떤 종류의 작업인지

Context Target
= 무엇을 대상으로 요청했는지

Skill
= 어떤 전문적인 방법으로 처리할지

Authority
= AI가 어디까지 행동할 수 있는지

Evidence
= 판단을 뒷받침하는 Repository 근거

GoalSpec
= 실행하기로 확정된 목표

TaskContract
= 실행 가능한 작업 계약
```

현재 v1에서는 `GoalSpec`부터 시작한다.

하지만 장기적으로는:

```
Human Request
↓
Intent Analysis
↓
판단 / 설명 / 리뷰 / 탐색 / 의사결정
↓
필요한 경우 Human Approval
↓
GoalSpec
↓
Planning
↓
TaskContract
↓
Execution
```

구조로 확장한다.

> **v1은 "주어진 Goal을 어떻게 실행 가능한 Task로 만들 것인가"를 해결한다. 이후에는 "Human의 요청이 무엇을 의미하는지 판단하고, Goal 자체가 아직 명확하지 않을 때 AI와 Human이 어떻게 탐색·판단·합의해서 Goal을 만들어낼 것인가"를 해결한다.**
