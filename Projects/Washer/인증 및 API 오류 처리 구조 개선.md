# 인증 및 API 오류 처리 구조 개선

## 1. 설계 배경

기존 Washer 관리자 페이지에서는 관리자 접근 권한을 확인하기 위해 AdminLayout에서 useGetMyInfo를 호출하고 있었다.

내 정보 조회가 실패하면 TanStack Query의 `isError` 상태를 기준으로 다음과 같은 처리를 수행했다.

```ts
if (isMyInfoError) {
  toast.error("로그인이 만료되었거나 유효하지 않습니다. 다시 로그인해주세요.");

  queryClient.clear();

  deleteCookie(COOKIE_KEYS.ACCESS_TOKEN);
  deleteCookie(COOKIE_KEYS.REFRESH_TOKEN);

  window.location.href = "/sign-in";
}
```

이 구조에서는 **내 정보 API 요청이 실패한 원인을 확인**하지 않고, 모든 오류를 로그인 만료로 판단했다.

따라서 실제 인증 만료뿐만 아니라 다음과 같은 오류가 발생했어도 **사용자 세션이 삭제**될 수 있었다.

- 서버 내부 오류
- 네트워크 연결 실패
- 요청 타임아웃
- 잘못된 API 응답 형식
- Zod Schema 검증 실패
- 일시적인 서버 응답 오류

특히 주요 조회 API에 Zod 런타임 검증을 적용하면서 이 문제가 명확하게 드러났다.

기존에는 서버 응답을 TS 타입으로만 지정했기 때문에 실제 응답이 선언된 타입과 달라도 런타임에서 확인하기 어려웠다.

Zod 검증을 적용한 이후에는 서버 응답이 Schema와 일치하지 않을 경우 검증 오류가 발생하고, 해당 오류가 TanStack Query이 오류 상태로 전달되었다.

그러나 `AdminLayout`에서는 오류 객체의 종류나 HTTP 상태 코드를 확인하지 않고 `isError` 여부만으로 로그인 만료를 판단했다.

그 결과, 인증과 관계없는 API 응답 검증 오류가 발생해도 다음과 같은 흐름으로 처리되엇다.

1. API 응답 형식 불일치
2. Zod Schema 검증 실패
3. TanStack Query isError
4. 로그인 만료로 판단
5. 전체 Query Cache 초기화
6. Access Token / Refresh Token 삭제
7. 로그인 페이지 이동

즉, 데이터 계약 오류가 인증 오류로 잘못 해석되면서 사용자가 강제로 로그아웃되는 문제가 발생할 수 있었다.

## 2. 기존 인증 처리 흐름

현재 Axios 인터셉터에서는 API 요청이 `401 Unauthorized` 를 반환하면 Refresh Token 을 이용해 Access Token 재발급을 시도한다.

1. API 요청
2. 401 authorized
3. Refresh Token 확인
4. Access Token 재발급 요청

토큰 재발급에 성공하면 새로운 Access Token과 Refresh Token을 저장하고, 실패했던 기존 요청을 다시 실행한다.

1. 토큰 재발급 성공
2. 새로운 Token 저장
3. 기존 요청 재실행
4. 정상 응답 반환

반대로 Refresh Token 이 없거나 토큰 재발급 요청까지 실패한 경우에는 오류가 TanStack Query로 전달된다.

1. 토큰 재발급 실패
2. 오류 반환
3. Tanstack Query error 상태

따라서 애플리케이션에서 실제 로그인 만료로 처리해야 하는 시점은 최초의 `401` 응답이 아니다.

최초 `401` 은 Axios 인터셉터에서 토큰 재발급을 통해 복구할 수 있는 오류이다.

Refresh Token을 이용한 재발급까지 실패해 더 이상 세션을 유지할 수 없는 경우에만 사용자 인증 정보를 삭제하고 로그인 페이지로 이동해야한다.

## 3. 문제 정의

기존 구조에서는 서로 다른 원인으로 발생한 오류가 모두 동일한 `isError` 상태로 처리되고 있었다.

1. 인증 만료, 권한 부족, 서버 오류, 네트워크 오류, API 응답 검증 오류, 알수 없는 어류
2. TanStack Query isError
3. 세션 초기화 및 로그인 페이지 이동

이 구조에는 다음과 같은 문제가 있다.

### 3-1. 인증과 무관한 오류에서도 세션이 삭제됨

서버 장애나 네트워크 오류처럼 인증과 관계없는 일시적ㅇ니 문제가 발생해도 Access Token 과 Refresh Token이 삭제된다.

사용자는 다시 로그인하더라도 같은 서버 오류를 경험할 수 있기 때문에, 로그아웃은 문제를 해결하지 못하고 사용자 경험만 악화시킨다.

### 3-2. API 계약 오류를 인증 오류로 오판함

Zod 검증 실패는 서버 응답과 클라이언트 Schema가 일치하지 않는 데이터 계약 문제이다.

하지만 기존 구조에서는 이를 로그인 만료로 처리하기 때문에 실제 원인을 확인하기 어렵다.

### 3-3. 오류 원인 추적이 어려움

모든 오류가 동일한 로그인 만료 메시지로 처리되기 때문에 다음 내용을 구분하기 어렵다.

- 서버가 응답하지 않는 것인지
- 사용자의 인증이 만료된 것인지
- 관리자 권한이 없는 것읹
- 서버 응답 형식이 잘못된 것인지
- 네트워크 연결이 끊긴 것인지

이로 인해 개발자가 오류를 재현하고 원인을 추적하는 과정도 복잡해진다.

### 3-4. 오류에 맞는 사용자 안내를 제공할 수 없음

오류의 종류에 따라 사용자에게 필요한 행동은 다르다.

- **인증 만료 :** 다시 로그인
- **권한 부족 :** 접근 제한 안내
- **네트워크 오류 :** 연결 확인 재시도
- **서버 오류 :** 잠시 후 다시 시도
- **응답 검증 오류 :** 서비스 오류 안내 및 개발자 확인

하지만 기존엔는 모든 경우에 로그인 페이지로 이동했기 때문에 상황에 맞는 안내와 복구 흐름을 제공할 수 없었다.

### 3-5. 세션 정리 로직이 UI에 직접 포함됨

`AdminLayout` 내부에서 다음 로직을 직접 수행하고 있었다.

- Query Cache 초기화
- Access Token 삭제
- Refresh Token 삭제
- 로그인 페이지 이동

이 때문에 인증 관련 책임과 화면 렌더링 책임이 하나의 컴포넌트에 함께 존재했다.

동일한 세션 정리 동작이 다른 화면에서도 필요해질 경우 코드가 중복될 가능성도 있었다.

## 4. 오류 분류 기준

오류를 단순히 성공과 실패로만 구분하지 않고, 원인에 따라 다음과 같이 분류할 필요가 있다.

### 인증 오류

사용자의 인증 정보를 더 이상 사용할 수 없는 경우다.

예시는 다음과 같다.

- Refresh Token이 존재하지 않음
- Refresh Token이 만료됨
- 토큰 재발급 API 실패
- 서버가 재인증이 필요하다고 판단함

이 경우에만 사용자 세션을 정리하고 로그인 페이지로 이동한다.

### 권한 오류

사용자 인증은 유효하지만 요청한 기능에 접근할 권한이 없는 경우다.

예시는 다음과 같다.

- 일반 사용자가 관리자 페이지에 접근
- 관리자 권한이 필요한 API에서 `403 Forbidden` 반환

이 경우에는 인증 토큰을 삭제할 필요가 없다.

접근 제한 메시지를 보여주고 사용 가능한 화면으로 이동시키는 방식으로 처리한다.

### 서버 오류

서버 내부 문제로 요청을 정상적으로 처리하지 못한 경우다.

예시는 다음과 같다.

- `500 Internal Server Error`
- `502 Bad Gateway`
- `503 Service Unavailable`

이 경우 사용자 세션은 유지하고, 잠시 후 다시 시도할 수 있도록 안내한다.

### 네트워크 오류

클라이언트가 서버로부터 응답을 받지 못한 경우다.

예시는 다음과 같다.

- 인터넷 연결 끊김
- 서버 연결 실패
- 요청 타임아웃
- DNS 또는 네트워크 환경 문제

이 경우에도 사용자 세션은 유지하고, 네트워크 상태 확인과 재시도 흐름을 제공한다.

### 응답 검증 오류

서버가 응답을 반환했지만 클라이언트에서 정의한 Zod Schema와 일치하지 않는 경우다.

예시는 다음과 같다.

- 필수 필드 누락
- 예상한 타입과 다른 타입 반환
- 예상하지 못한 상태값 반환
- nullable 여부 불일치

이 오류는 인증 문제가 아니라 서버와 클라이언트 간 API 계약 문제다.

사용자의 세션을 유지하면서 개발 단계에서 원인을 추적할 수 있도록 별도로 구분해야 한다.

### 알 수 없는 오류

앞선 기준으로 분류할 수 없는 오류다.

이 경우 일반적인 오류 안내를 제공하되, 원본 오류 정보를 유지해 추후 분석할 수 있도록 한다.

## 5. 설계 목표

이번 리팩토링의 목표는 모든 오류를 하나의 실패 상태로 처리하는 것이 아니라, 오류의 원인을 분류하고 각 상황에 맞는 동작을 수행할 수 있는 구조를 만드는 것이다.

### 5.1 실제 인증 만료에서만 세션 정리

Refresh Token을 이용한 토큰 재발급까지 실패한 경우에만 다음 처리를 수행한다.

```
Query Cache 초기화
Access Token 삭제
Refresh Token 삭제
로그인 페이지 이동
```

서버 오류, 네트워크 오류, Zod 검증 오류에서는 사용자 세션을 유지한다.

### 5.2 오류 유형별 처리 흐름 분리

HTTP 상태 코드와 오류 발생 지점을 기준으로 오류를 구분한다.

```
401 또는 토큰 재발급 실패
→ 인증 오류

403
→ 권한 오류

500 이상
→ 서버 오류

응답 없음
→ 네트워크 오류

ZodError
→ 응답 검증 오류
```

분류된 오류를 기준으로 사용자 안내, 재시도, 라우팅, 세션 정리 여부를 결정한다.

### 5.3 공통 오류 형태 정의

AxiosError, ZodError 등 외부 라이브러리마다 다른 오류 형태를 UI에서 직접 판단하지 않도록 애플리케이션에서 사용하는 공통 오류 타입을 정의한다.

```tsx
type AppErrorType =
  | "AUTHENTICATION"
  | "FORBIDDEN"
  | "SERVER"
  | "NETWORK"
  | "VALIDATION"
  | "UNKNOWN";

type AppError = {
  type: AppErrorType;
  message: string;
  status?: number;
  cause?: unknown;
};
```

API와 데이터 검증 계층에서 발생한 오류를 `AppError` 형태로 변환하고, UI에서는 `error.type`을 기준으로 처리하도록 구성한다.

### 5.4 세션 정리 책임 분리

Query Cache 초기화와 토큰 삭제 로직을 `AdminLayout`에서 분리한다.

```tsx
clearAuthSession(queryClient);
```

또는 각 책임을 다음과 같이 나눌 수 있다.

```tsx
clearAuthCookies();
queryClient.clear();
redirectToSignIn();
```

이를 통해 UI 컴포넌트는 오류에 따른 화면 처리와 라우팅 판단에 집중하고, 인증 데이터 정리는 공통 함수에서 담당하도록 한다.

### 5.5 오류 원인 추적 가능성 확보

오류를 분류하더라도 원본 오류를 완전히 제거하지 않고 `cause`로 유지한다.

이를 통해 개발 환경이나 오류 추적 도구에서 다음 정보를 확인할 수 있도록 한다.

- 원본 Axios 오류
- HTTP 상태 코드
- 서버 응답 내용
- Zod 검증 실패 경로
- 예상 타입과 실제 값

## 6. 개선 전후 흐름

### 기존 흐름

```
API 요청 실패
        ↓
TanStack Query isError
        ↓
모든 오류를 인증 만료로 판단
        ↓
Query Cache 초기화
        ↓
Token 삭제
        ↓
로그인 페이지 이동
```

### 개선 흐름

```
API 요청 또는 응답 검증 실패
        ↓
오류 원인 분석
        ↓
공통 AppError로 변환
        ↓
오류 유형별 처리
```

```
AUTHENTICATION
→ 세션 정리
→ 로그인 페이지 이동

FORBIDDEN
→ 세션 유지
→ 접근 제한 안내 및 페이지 이동

SERVER
→ 세션 유지
→ 서버 오류 안내 및 재시도

NETWORK
→ 세션 유지
→ 네트워크 확인 안내 및 재시도

VALIDATION
→ 세션 유지
→ API 계약 오류 안내 및 원인 기록

UNKNOWN
→ 세션 유지
→ 일반 오류 안내
```

## 7. 설계 원칙

이번 오류 처리 구조는 다음 원칙을 기준으로 설계한다.

### 오류 상태와 인증 상태를 동일하게 취급하지 않는다

API 요청이 실패했다는 사실만으로 사용자의 인증이 만료되었다고 판단하지 않는다.

인증 만료는 명확하게 식별된 인증 오류에서만 처리한다.

### 복구 가능한 오류에서는 사용자 상태를 유지한다

네트워크 오류나 서버 오류처럼 일시적으로 복구될 수 있는 상황에서는 사용자의 Token과 Query Cache를 불필요하게 삭제하지 않는다.

### 오류 분류는 데이터 경계에서 수행한다

UI 컴포넌트마다 AxiosError와 ZodError를 직접 확인하지 않는다.

API 또는 공통 오류 변환 계층에서 오류를 애플리케이션 공통 형태로 정규화한다.

### UI는 오류에 따른 사용자 경험을 담당한다

UI에서는 오류를 생성하거나 해석하는 대신, 이미 분류된 오류를 기준으로 안내 메시지, 재시도 버튼, 페이지 이동 여부를 결정한다.

### 원본 오류 정보는 보존한다

사용자에게는 이해하기 쉬운 메시지를 제공하되, 개발자가 원인을 확인할 수 있도록 원본 오류와 상세 정보를 유지한다.

## 8. 작업 범위

이번 리팩토링에서는 다음 작업을 진행한다.

1. 애플리케이션 공통 오류 타입 정의
2. Axios 오류 분류 함수 구현
3. Zod 검증 오류를 공통 오류 형태로 변환
4. 토큰 재발급 실패를 인증 만료 오류로 명확히 구분
5. 세션 정리 로직 공통화
6. `AdminLayout`에서 오류 유형별 처리
7. 인증·권한·서버·네트워크·검증 오류별 사용자 안내 분리
8. 오류 유형별 TanStack Query 재시도 정책 검토

## 9. 기대 결과

이번 리팩토링을 통해 다음과 같은 결과를 기대할 수 있다.

- 인증과 관계없는 오류로 인한 불필요한 강제 로그아웃 방지
- 서버 오류와 API 계약 오류에서도 사용자 세션 유지
- 실제 인증 만료인 경우에만 Token과 Query Cache 정리
- 오류 원인에 맞는 사용자 안내와 재시도 흐름 제공
- Axios 오류와 Zod 오류를 일관된 형태로 처리
- 인증 관련 책임과 UI 렌더링 책임 분리
- API 응답 오류의 원인 추적 가능성 향상
- 이후 다른 API와 화면에도 동일한 오류 처리 기준 적용 가능### 권한 오류

사용자 인증은 유효하지만 요청한 기능에 접근할 권한이 없는 경우다.

예시는 다음과 같다.

- 일반 사용자가 관리자 페이지에 접근
- 관리자 권한이 필요한 API에서 `403 Forbidden` 반환

이 경우에는 인증 토큰을 삭제할 필요가 없다.

접근 제한 메시지를 보여주고 사용 가능한 화면으로 이동시키는 방식으로 처리한다.

### 서버 오류

서버 내부 문제로 요청을 정상적으로 처리하지 못한 경우다.

예시는 다음과 같다.

- `500 Internal Server Error`
- `502 Bad Gateway`
- `503 Service Unavailable`

이 경우 사용자 세션은 유지하고, 잠시 후 다시 시도할 수 있도록 안내한다.

### 네트워크 오류

클라이언트가 서버로부터 응답을 받지 못한 경우다.

예시는 다음과 같다.

- 인터넷 연결 끊김
- 서버 연결 실패
- 요청 타임아웃
- DNS 또는 네트워크 환경 문제

이 경우에도 사용자 세션은 유지하고, 네트워크 상태 확인과 재시도 흐름을 제공한다.

### 응답 검증 오류

서버가 응답을 반환했지만 클라이언트에서 정의한 Zod Schema와 일치하지 않는 경우다.

예시는 다음과 같다.

- 필수 필드 누락
- 예상한 타입과 다른 타입 반환
- 예상하지 못한 상태값 반환
- nullable 여부 불일치

이 오류는 인증 문제가 아니라 서버와 클라이언트 간 API 계약 문제다.

사용자의 세션을 유지하면서 개발 단계에서 원인을 추적할 수 있도록 별도로 구분해야 한다.

### 알 수 없는 오류

앞선 기준으로 분류할 수 없는 오류다.

이 경우 일반적인 오류 안내를 제공하되, 원본 오류 정보를 유지해 추후 분석할 수 있도록 한다.

## 5. 설계 목표

이번 리팩토링의 목표는 모든 오류를 하나의 실패 상태로 처리하는 것이 아니라, 오류의 원인을 분류하고 각 상황에 맞는 동작을 수행할 수 있는 구조를 만드는 것이다.

### 5.1 실제 인증 만료에서만 세션 정리

Refresh Token을 이용한 토큰 재발급까지 실패한 경우에만 다음 처리를 수행한다.

```
Query Cache 초기화
Access Token 삭제
Refresh Token 삭제
로그인 페이지 이동
```

서버 오류, 네트워크 오류, Zod 검증 오류에서는 사용자 세션을 유지한다.

### 5.2 오류 유형별 처리 흐름 분리

HTTP 상태 코드와 오류 발생 지점을 기준으로 오류를 구분한다.

```
401 또는 토큰 재발급 실패
→ 인증 오류

403
→ 권한 오류

500 이상
→ 서버 오류

응답 없음
→ 네트워크 오류

ZodError
→ 응답 검증 오류
```

분류된 오류를 기준으로 사용자 안내, 재시도, 라우팅, 세션 정리 여부를 결정한다.

### 5.3 공통 오류 형태 정의

AxiosError, ZodError 등 외부 라이브러리마다 다른 오류 형태를 UI에서 직접 판단하지 않도록 애플리케이션에서 사용하는 공통 오류 타입을 정의한다.

```tsx
type AppErrorType =
  | "AUTHENTICATION"
  | "FORBIDDEN"
  | "SERVER"
  | "NETWORK"
  | "VALIDATION"
  | "UNKNOWN";

type AppError = {
  type: AppErrorType;
  message: string;
  status?: number;
  cause?: unknown;
};
```

API와 데이터 검증 계층에서 발생한 오류를 `AppError` 형태로 변환하고, UI에서는 `error.type`을 기준으로 처리하도록 구성한다.

### 5.4 세션 정리 책임 분리

Query Cache 초기화와 토큰 삭제 로직을 `AdminLayout`에서 분리한다.

```tsx
clearAuthSession(queryClient);
```

또는 각 책임을 다음과 같이 나눌 수 있다.

```tsx
clearAuthCookies();
queryClient.clear();
redirectToSignIn();
```

이를 통해 UI 컴포넌트는 오류에 따른 화면 처리와 라우팅 판단에 집중하고, 인증 데이터 정리는 공통 함수에서 담당하도록 한다.

### 5.5 오류 원인 추적 가능성 확보

오류를 분류하더라도 원본 오류를 완전히 제거하지 않고 `cause`로 유지한다.

이를 통해 개발 환경이나 오류 추적 도구에서 다음 정보를 확인할 수 있도록 한다.

- 원본 Axios 오류
- HTTP 상태 코드
- 서버 응답 내용
- Zod 검증 실패 경로
- 예상 타입과 실제 값

## 6. 개선 전후 흐름

### 기존 흐름

```
API 요청 실패
        ↓
TanStack Query isError
        ↓
모든 오류를 인증 만료로 판단
        ↓
Query Cache 초기화
        ↓
Token 삭제
        ↓
로그인 페이지 이동
```

### 개선 흐름

```
API 요청 또는 응답 검증 실패
        ↓
오류 원인 분석
        ↓
공통 AppError로 변환
        ↓
오류 유형별 처리
```

```
AUTHENTICATION
→ 세션 정리
→ 로그인 페이지 이동

FORBIDDEN
→ 세션 유지
→ 접근 제한 안내 및 페이지 이동

SERVER
→ 세션 유지
→ 서버 오류 안내 및 재시도

NETWORK
→ 세션 유지
→ 네트워크 확인 안내 및 재시도

VALIDATION
→ 세션 유지
→ API 계약 오류 안내 및 원인 기록

UNKNOWN
→ 세션 유지
→ 일반 오류 안내
```

## 7. 설계 원칙

이번 오류 처리 구조는 다음 원칙을 기준으로 설계한다.

### 오류 상태와 인증 상태를 동일하게 취급하지 않는다

API 요청이 실패했다는 사실만으로 사용자의 인증이 만료되었다고 판단하지 않는다.

인증 만료는 명확하게 식별된 인증 오류에서만 처리한다.

### 복구 가능한 오류에서는 사용자 상태를 유지한다

네트워크 오류나 서버 오류처럼 일시적으로 복구될 수 있는 상황에서는 사용자의 Token과 Query Cache를 불필요하게 삭제하지 않는다.

### 오류 분류는 데이터 경계에서 수행한다

UI 컴포넌트마다 AxiosError와 ZodError를 직접 확인하지 않는다.

API 또는 공통 오류 변환 계층에서 오류를 애플리케이션 공통 형태로 정규화한다.

### UI는 오류에 따른 사용자 경험을 담당한다

UI에서는 오류를 생성하거나 해석하는 대신, 이미 분류된 오류를 기준으로 안내 메시지, 재시도 버튼, 페이지 이동 여부를 결정한다.

### 원본 오류 정보는 보존한다

사용자에게는 이해하기 쉬운 메시지를 제공하되, 개발자가 원인을 확인할 수 있도록 원본 오류와 상세 정보를 유지한다.
