# 파라메트릭 비주얼 제너레이터 구현을 위한 기술 정리

## 1. 파라메트릭 비주얼 제너레이터란?

사용자가 슬라이더, 색상 선택기, 입력창 등의 UI를 통해 값을 조절하면, 해당 값에 따라 그래픽 결과가 실시간으로 변하는 시스템이다.

예를 들어 사용자가 다음 값을 바꿀 수 있다.

- 그리드 가로 & 세로 칸 수
- 밝기 구간
- 색상
- 블록 너비와 높이
- 도형 종류
- 표현 모드

입력된 값은 그래픽 계산 로직에 전달되고, 계산 결과가 Canvas, SVG, WebGL 등의 렌더링 영역에 다시 그려진다.

## 2 기본 구조

파라메트릭 제너레이터는 크게 세 부분으로 나눌 수 있다.

### 2-1. 파라미터 상태

사용자가 조절하는 값을 저장한다.

이번 프로젝트에서는 다음과 같은 값이 해당된다.

- **column :** 가로 칸 수
- **rows :** 세로 칸 수
- **mode :** width 또는 height
- **segments :** 루마 구간 설정
- **color :** 구간별 색상
- **widthRatio :** 구간별 너비 비율
- **heightRatio :** 구간별 높이 비율
- **shape :** 블록, 원, 마름모 등의 도형 종류

### 2-2. 계산 로직

입력된 파라미터와 원본 이미지를 바탕으로 각 셀의 결과를 계산한다.

이번 프로젝트에서는 다음 과정이 포함된다.

1. 이미지를 그리드 단위로 샘플링한다.
2. 각 셀에 해당하는 RGB 값을 가져온다.
3. RGB 값을 루마값으로 변환한다.
4. 루마값이 어느 구간에 속하는지 판단한다.
5. 구간에 대응하는 색상과 크기를 결정한다.
6. 각 셀의 위치와 도형 정보를 생성한다.

### 2-3. 렌더링

계산된 결과를 화면에 그린다.

파라미터가 바귀면 기존 결과를 지우고 새 결과를 다시 렌더링한다. 영상이나 애니메이션을 처리한다면 `requestAnimationFrame`을 이용해 프레임마다 갱신한다.

## 3. 프로젝트 구성에 필요한 기술

### 3-1. 개발 환경: Vite

Vite는 Reacts나 p5.js 같은 프레임워크가 아니라, 프로젝트를 실행하고 빌드하기 위한 개발 도구다.

#### 사용하는 이유

- 초기 프로젝트 설정이 간단함
- 개발 서버 실행이 빠름
- 코드 수정 결과가 빠르게 반영됨
- 단독 실험 프로젝트를 만들기 적합함
- Next.js의 서버 기능이 필요하지 않은 프로젝트에 가벼움

이번 프로젝트는 로그인, 서버 렌더링, SEO 등이 핵심이 아니기 때문에 Next.js보다 Vite가 단순하다.

다만 Vite 자체가 그래픽을 만들어주는 것은 아니다. 실제 그래픽 처리는 **Canvas, p5.js, PixJS** 등의 도구가 담당한다.

### 3-2. UI 구성: React

React는 제너레이터의 설정 UI와 상태를 관리하는 데 사용할 수 있다.

#### React가 담당할 부분

- 파일 업로드 UI
- 슬라이더
- 색상 선택기
- 모드 전환
- 루마 구간 목록
- 설정 초기호
- 파라미터 상태 관리
- 설정값을 렌더러에 전달

#### React 가 직접 당당하지 않는 부분

- 픽셀 단위 이미지 처리
- Canvas에 수백 개의 도형 그리기
- 영상 프레임 반복 처리

이런 무거운 그래픽 작업은 React 컴포넌트로 각각 렌더링하기 보다 Canvas API 또는 그래픽 라이브러리에서 처리하는 것이 적합하다.

## 4. 그래픽 렌더링 도구 비교

### 4-1. Canvas 2D API

브라우저에 기본으로 제공되는 2D 그래픽 API다.

#### 장점

- 별도 그래픽 라이브러리가 필요 없음
- 이미지 픽셀 데이터에 접근 가능
- 이미지와 영상을 Canvas에 그릴 수 있음
- 직사각형, 원, 선 등의 도형을 직접 렌더링 가능
- 이번 프로젝트의 기본 원리를 정확하게 학습할 수 있음

#### 단점

- 좌표 계산과 렌더링을 직접 작성해야 함
- 복잡한 기능이 많아지면 코드 관리가 어려워질 수 있음
- 대량의 픽셀이나 도형을 실시간 처리할 때 성능 한계가 생길 수 있음

#### 이번 프로젝트와의 적합성

매우 높음 -> 이미지의 픽셀을 읽기 위해 다음 기능이 필요하다.

이미지 픽셀을 읽기 위해 다음 기능이 필요하다.

- `drawImage`
- `getImageData`
- `clearReact`
- `fillReact`
- `requestAnimationFrame`

### 4-2. p5.js

Canvas 기반 크리에이티브 코딩을 쉽게 작성하도록 도와주는 라이브러리이다.

#### 장점

- 이미지와 픽셀 처리 API가 비교적 간단함
- 크리에이티브 코딩 예제와 자료가 많음
- `setup`, `draw` 형태로 렌더링 흐름을 이해하기 쉬움
- 도형, 색상, 백터, 노이즈 등의 기능을 제공함
- 빠른 시각 실험에 적합함

#### 단점

- React와 함께 사용할 때 생명주기를 따로 연결해야 함
- 내부 동작을 모르면 렌더링 제어가 애매해질 수 있음
- 규모가 커지면 p5.js 코드와 UI 상태의 경계가 복잡해질 수 있음

#### 이번 프로젝트와의 적합성

기술 검증과 알고리즘 실험에는 적합하다.

특히 이미지 밝기를 읽고 컬러 블록을 배치하는 첫 실험을 빠르게 해볼 때 유용하다. 다만 실제 납품용 툴에서는 React UI 와 p5.js 렌더러의 구조를 명확히 분리해야 한다.

### 4-3. PixiJS

WebGL을 기반으로 많은 2D 그래픽을 빠르게 렌더링하는 라이브러리다.

#### 장점

- Canvas 보다 많은 개체를 빠르게 렌더링 할 수 있음
- GPU를 활용함
- 이미지, 스프라이트, 필터 처리에 적합함
- 영상이나 실시간 그래픽으로 확장할 때 유리함

#### 단점

- Canvas보다 학습해야 할 개념이 많음
- 현재 프로젝트의 초기 기능에는 과할 수 있음
- 픽셀 샘플링 로직은 별도로 구현해야 함

#### 이번 프로젝트와의 적합성

1차 구현보다는 성능 문제가 확인된 이후의 대안이다.

처음부터 PixiJs로 시작하기 보다, Canvas로 구조를 검증한 뒤 영상 처리나 고밀도 그리드에서 성능이 부족할 때 전환을 검토하는 것이 적절하다.

### 4-4. SVG

각 도형을 DOM 요소처럼 다루는 백터 그래픽 방식이다.

#### 장점

- 도형마다 개별 이벤트를 연결하기 쉬움
- 백터 기반이라 확대해도 선명함
- CSS를 이용해 스타일링 가능
- 결과물을 SVG 형식으로 저장하기 쉬움

#### 단점

- 셀 수가 많아지면 DOM 요소가 지나치게 많아짐
- 영상처럼 프레임마다 전체 결과가 바뀌는 처리에는 불리함
- 픽셀 데이터를 읽는 용도로는 Canvas가 필요함

#### 이번 프로젝트와의 적합성

기본 렌더링 방식으로는 우선순위가 낮다.

다만 최종 결과물을 SVG로 내보내야 한다면 별도읯 ㅜㄹ력 포맷으로 고려할 수 있다.

### 4-5. Three.js / React Three Fiber

웹에서 3D 그래픽을 구현하기 위한 도구다.

#### 적합한 경우

- 3D 공간
- 카메라 이동
- 조명
- 입체 오브젝트
- 3D 모델의 크기와 형태 조절

#### 이번 프로젝트와의 적합성

현재 요구사항은 2D 이미지 모자이크 제너레이터이므로 필요하지 않다.

벽돌이라는 컨셉은 있어도 실제 3D 벽돌을 만드는 것이 아니라, 2D 벽돌 모양 그리드를 만드는 것이므로 Three.js를 사용할 이유는 적다.

### 4-6. WebGL과 Shader

GPU를 이용해 픽셀 단위 연산을 빠르게 처리하는 기술이다.

#### 적합한 경우

- 고해상도 영상 실시간 처리
- 수십만 개 이사으이 도형
- 복잡한 이미지 필터
- 픽셀마다 반복되는 계산
- Canvas 2D로 목표 프레임을 유지하지 못하는 경우

#### 이번 프로젝트와의 적합성

장기 확장 단계에서 고려할 수 있다.

초기에는 WebGL과 셰이더까지 학습하면 기술 조사 범위가 지나치게 커진다. 먼저 Canvas 2D로 구현하고 실제 성능 병목이 확인된 뒤 선택하는 것이 맞다.

## 5. 파라미터 UI 라이브러리

### 5-1. Tweakpane

그래픽 실험용 파라미터 패널을 빠르게 만들 수 있는 라이브러리이다.

#### 제공 기능

- 숫자 슬라이더
- 색상 선택기
- 체크박스
- 드롭다운
- 폴더 형태의 설정 그룹
- 값 변경 이벤트

#### 적합한 용도

개발자용 프로토타입과 내부 실험 도구

초기에는 디자인된 UI를 직접 만들기보다 Tweakpane을 붙여 파라미터를 빠르게 테스트할 수 있다.

### 5-2. lil-gui

Tweakpane과 비슷한 그래픽 제어 패널 라이브러리다.

#### 적합한 용도

- 빠른 프로토타입
- 개발 중 변수 조정
- 크리에이티브 코디 실험

Tweakpane과 lil-gui 중 하나만 선택하면 된다. 둘 다 동시에 사용할 필요는 없다.

### 5-3. 직접 React UI 구현

실제 사용자가 사용하는 상업용 툴이라면 최종적으로는 React 컴포넌트로 UI를 직접 만드는 것이 적합하다.

#### 권장 흐름

1. Tweakpane으로 기능과 파라미터 검증
2. 필요한 항목 확정
3. 확정된 항목을 REact UI로 다시 구현
4. 디자인 시스템과 브랜드 스타일 적용

처음부터 완성된 UI를 만들려면 파라미터가 계속 바뀔 때 수정 비용이 커진다.

## 6. 이번 프로젝트 조합\_예정

### 1차 기술 검증

```
Vite
+ TypeScript
+ Canvas 2D API
+ Tweakpane
```

#### 목적

- 이미지 업로드
- 그리드 생성
- 루마값 계산
- 밝기 구간 매핑
- 색상 및 블록 킉 조절
- width/height 모드 검증

### 실제 UI가 포함된 프로토타입

```
Vite
+ React
+ TypeScript
+ Canvas 2D API
+ Tweakpane 또는 React 기반 컨트롤 UI
```

#### 역할 분리

- **React :** UI와 설정값 관리
- **Canvas :** 이미지 분석 및 결과 렌더링
- **TypeScript :** 파라미터와 구간 설정의 타입 정의
- **Vite :** 개발 환경과 빌드
- **Tweakpane :** 초기 파라미터 실험

### 성능 확장 단계

```
Vite
+ React
+ TypeScript
+ PixiJS 또는 WebGL
```

but 다음 문제가 확인됐을 때만 고려한다.

- 영상이 심하게 끊김
- 고해상도 출력이 느림
- 그리드 수를 늘렸을 때 프레임이 급격히 떨어짐
- 복잡한 필터 연산이 필요함.

## 8. 구현 단계

### 1단계: Vanilla Canvas 실험

- 이미지 한 장을 Canvas에 표시
- 이미지 픽셀 읽기
- 루마값 계산
- 낮은 해상도의 컬러 블록으로 다시 그리기

이 단계에서는 React와 UI를 붙이지 않아도 된다.

### 2단계: 파라미터 연결

- 가로·세로 칸 수
- 루마 구간
- 색상
- width/height 배율
- 표시 모드

Tweakpane을 사용해 값을 변경하면서 즉시 결과를 확인한다.

### 3단계: 로직 분리

- 이미지 샘플링 함수
- 루마 계산 함수
- 구간 탐색 함수
- 그리드 생성 함수
- 도형 렌더링 함수

각 기능을 순수 함수 또는 별도 모듈로 나눈다.

### 4단계: React UI 적용

- 이미지 업로드
- 컨트롤 패널
- 구간별 설정 UI
- 초기화
- 모드 전환

Canvas 인스턴스는 `useRef`로 관리하고 React 상태가 바뀔 때 렌더링 함수를 호출한다.

### 5단계: 영상 처리

- 영상 프레임을 Canvas에 복사
- 프레임별 이미지 샘플링
- `requestAnimationFrame`을 이용한 반복 렌더링
- 프레임 속도와 해상도 조절

### 6단계: 확장 기능

- 벽돌 그리드
- 동적 구간 추가·삭제
- 도형 교체
- 결과물 내보내기
- 프리셋 저장

## 9. 성능 관리 원칙

### React와 렌더링 분리

- Canvas와 각 셀을 React 컴포넌트로 만들지 않는다.
- React는 설정값만 관리하고, 반복적인 도형 그리기는 Canvas가 담당해야 한다.

### 불필요한 상태 업데이트 방지

- 슬라이더를 움직일 때마다 React 컴포넌트 전체가 무겁게 다시 렌덜이 되지 않도록 한다.
- Canvas와 렌더러는 `useRef`로 유지하고 필요한 값만 유지한다.

### 입력 이미지 해상도 축소

- 원본 이미지가 4k라고 해고 그리드가 50x50이면 모든 원본 픽셀을 분석할 필요가 없다.
- 분석용 Canvas를 작은 해상도로 만들어 그리드 크기에 맞게 샘플링하면 연산량을 줄일 수 있다.

### 실시간 렌더링 요청 통합

- 슬라이더 변경 이벤트마다 즉시 여러 번 다시 그리기보다, 다음 애니메이션 프레임에 한 번만 렌더링하도록 요청을 합칠 수 있다.

### 성능 도구는 실제 문제가 생긴 뒤 도입

PixiJS, WebGL, Web Worker, OffscreenCanvas 등은 실제 병목을 측정한 뒤 사용한다. 처음부터 모두 적용하면 개발 난이도만 올라갈 수 있다.
