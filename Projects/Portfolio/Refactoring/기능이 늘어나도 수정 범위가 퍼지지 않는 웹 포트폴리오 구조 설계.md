## 기능이 늘어나도 수정 범위가 퍼지지 않는 웹 포트폴리오 구조 설계

> 하나의 Capability 영역을 Build와 Projects로 분리하고, 화면의 의미와 코드가 변경되는 이유를 프로젝트 전체 구조에 반영한 과정

## 들어가며

초기 포트폴리오에서는 화면을 설계하고 구현하는 과정과, 완성된 프로젝트 결과물을 하나의 `Capability` 영역에서 함께 관리했습니다.

```
Capability
├─ Intro
├─ Structure
├─ AI
├─ Visual
├─ Project Navigator
└─ Closing
```

처음에는 모두 개발 역량을 설명하는 콘텐츠라는 공통점이 있었기 때문에 하나의 영역으로 구성해도 큰 문제가 없었습니다.

하지만 콘텐츠가 구체화될수록 `Capability` 안에는 성격이 다른 두 가지 정보가 함께 존재하게 됐습니다.

```
어떻게 화면을 설계하고 구현하는가
+
그 결과로 무엇을 만들어 왔는가
```

Structure, AI, Visual은 제가 화면을 설계하고 구현하는 방식을 설명하는 영역이었습니다.

반면 Project Navigator와 프로젝트 상세 화면은 실제로 완성한 결과물을 탐색하는 영역이었습니다.

두 영역은 사용자에게 전달하는 정보도 달랐고, 수정되는 이유도 달랐습니다. 그러나 코드에서는 하나의 `Capability` 이름 아래 다음 파일들이 함께 관리되고 있었습니다.

```
컴포넌트
애니메이션
콘텐츠 데이터
스타일
이미지 경로
상세 페이지 라우팅
```

이 상태에서는 Build 영역의 내용을 수정할 때 Projects 관련 파일까지 함께 확인해야 했고, 특정 파일이 화면 설계 과정과 프로젝트 결과물 중 어느 책임에 속하는지도 이름만으로 판단하기 어려웠습니다.

그래서 이번 리팩토링에서는 단순히 파일을 더 작은 단위로 나누는 것이 아니라, 다음 질문을 기준으로 프로젝트 구조를 다시 설계했습니다.

> 이 코드는 어떤 화면을 위한 것인가?

> 이 파일은 어떤 이유로 함께 변경되는가?

> 사용자가 이해하는 화면의 경계와 코드의 경계가 일치하는가?

---

# 1. 기술 종류만으로 나눈 구조의 한계

프론트엔드 프로젝트는 일반적으로 파일의 기술적 역할에 따라 상위 폴더를 구분합니다.

```
components/
animations/
data/
styles/
assets/
```

이 구분은 필요합니다.

컴포넌트와 애니메이션, 데이터와 스타일은 서로 다른 책임을 가지고 있기 때문입니다.

하지만 프로젝트가 커지면 기술 종류만으로는 특정 기능과 관련된 파일을 한눈에 파악하기 어렵습니다.

예를 들어 `Capability` 영역의 프로젝트 탐색 기능을 수정하려면 다음 위치를 함께 확인해야 했습니다.

```
components/.../capability
animations/.../capability
data/.../capability
styles/.../capability
assets/capabilityImages.ts
app/capability/[id]
```

파일은 기술 종류에 따라 나뉘어 있었지만, 하나의 `Capability` 안에 서로 다른 의미의 기능이 함께 포함돼 있었습니다.

즉, 상위 폴더 구조는 정리돼 있었지만 **도메인 내부의 책임 경계가 충분히 드러나지 않는 상태**였습니다.

이 문제를 해결하기 위해 상위에서는 기술적 책임을 유지하고, 각 책임 내부에서는 화면의 의미와 변경 이유를 기준으로 도메인을 분리했습니다.

```
상위 구조
→ 파일이 어떤 기술적 책임을 가지는가?

내부 도메인
→ 파일이 어떤 화면과 기능을 위해 존재하는가?
```

---

# 2. Capability를 Build와 Projects로 분리했습니다

먼저 `Capability`가 담당하던 두 가지 의미를 분리했습니다.

## Build

화면을 설계하고 구현하는 방식을 설명합니다.

```
Build
├─ Intro
├─ Structure
├─ AI
└─ Visual
```

- 화면과 정보의 구조를 어떻게 설계했는지
- AI 도구를 어떤 기준으로 활용하는지
- 시각 요소와 인터랙션을 어떻게 구현하는지

## Projects

완성한 프로젝트 결과물을 탐색합니다.

```
Projects
├─ Navigator
├─ Project Detail
└─ Closing
```

- 어떤 프로젝트를 만들었는지
- 프로젝트별 화면과 핵심 내용을 어떻게 보여줄지
- 목록과 미리보기를 어떻게 연결할지
- 상세 페이지로 어떻게 이동할지

기존 구조는 다음과 같았습니다.

```
CapabilityStage
├─ CapabilityIntroScene
├─ ExperienceCapabilityScene
├─ CapabilityNavigatorScene
└─ CapabilityClosingScene
```

리팩토링 이후에는 다음처럼 분리했습니다.

```
BuildStage
├─ BuildIntroScene
└─ BuildExperienceScene
   ├─ Structure
   ├─ AI
   └─ Visual

ProjectsStage
├─ ProjectsNavigatorScene
└─ ProjectsClosingScene
```

이 변화는 단순한 이름 변경이 아닙니다.

사용자가 포트폴리오를 읽는 흐름과 코드 구조를 일치시킨 것입니다.

```
Build
→ 나는 어떻게 화면을 만드는가?

Projects
→ 그래서 무엇을 만들었는가?
```

두 영역이 전달하는 질문이 달라졌기 때문에 코드에서도 서로 다른 도메인으로 분리했습니다.

---

# 3. 분리를 컴포넌트 폴더에서 끝내지 않았습니다

도메인을 분리할 때 컴포넌트 경로만 바꾸면 관련 코드가 여전히 기존 이름 아래 섞여 있게 됩니다.

예를 들어 다음 정도로만 변경했다면:

```
components/build/
components/projects/
```

Animation, Data, Style, Image는 여전히 `capability` 이름 아래 남아 있을 수 있습니다.

그러면 화면 컴포넌트의 위치만 달라졌을 뿐, 특정 도메인을 수정할 때 여러 경계를 다시 오가야 하는 문제는 해결되지 않습니다.

그래서 Build와 Projects의 경계를 다음 영역 전체에 동일하게 반영했습니다.

```
components/
├─ build/
└─ projects/

animations/
├─ build/
└─ projects/

data/
├─ build/
└─ projects/

styles/
├─ build/
└─ projects/

assets/
├─ buildImages.ts
└─ projectsImages.ts

public/images/
├─ build/
└─ projects/

app/
└─ projects/[id]/
```

이를 통해 특정 도메인에 포함되는 파일이 같은 이름과 경계 아래 놓이도록 만들었습니다.

## Build를 수정할 때

```
components/features/build
components/scenes/build
animations/build
data/build
styles/features/build
assets/buildImages.ts
public/images/build
```

## Projects를 수정할 때

```
components/features/projects
components/scenes/projects
animations/projects
data/projects
styles/features/projects
assets/projectsImages.ts
public/images/projects
app/projects/[id]
```

특정 기능을 수정할 때 관련 파일을 찾기 위해 `Capability` 내부를 모두 탐색하지 않아도 됩니다.

폴더 이름만 보더라도 해당 코드가 어떤 화면을 위한 것인지 예상할 수 있게 됐습니다.

---

# 4. 화면은 Stage → Scene → Feature 구조로 나눴습니다

컴포넌트는 크기만 기준으로 나누지 않았습니다.

사용자가 화면을 경험하는 단위와 각 컴포넌트의 책임을 기준으로 세 계층을 정의했습니다.

```
Stage
→ 하나의 큰 스크롤 챕터

Scene
→ Stage 안에서 사용자가 보는 시각적 장면

Feature
→ Scene을 구성하는 기능성 UI
```

---

## Stage

Stage는 페이지의 큰 스크롤 흐름을 구성합니다.

```
IntroStage
BuildStage
ProjectsStage
ContactStage
```

Stage는 다음 역할만 담당합니다.

- Stage root ref 관리
- Scene 배치
- Stage 전용 Animation Hook 연결
- Stage 단위 상태 연결
- 분석 이벤트 연결

예를 들어 `BuildStage`는 Build 관련 화면을 직접 세부 구현하지 않고, Build를 구성하는 Scene을 배치합니다.

```tsx
<section ref={stageRef}>
  <BuildIntroScene />
  <BuildExperienceScene />
</section>
```

스크롤 흐름을 변경하려면 Stage와 Stage Hook을 확인하면 됩니다.

---

## Scene

Scene은 Stage 안에서 하나의 시각적 장면을 구성합니다.

```
BuildIntroScene
BuildExperienceScene
ProjectsNavigatorScene
ProjectsClosingScene
```

Scene은 다음 역할을 담당합니다.

- 화면의 JSX 구조 구성
- Feature Component 조합
- Animation target 제공
- 장면 단위의 정보 위계 표현

예를 들어 `BuildExperienceScene`은 Build 영역에서 전달할 세 가지 경험을 조합합니다.

```
BuildExperienceScene
├─ BuildStructureBlock
├─ BuildAIBlock
└─ BuildVisualBlock
```

장면의 정보 구성이나 배치를 변경하려면 Scene을 확인하면 됩니다.

---

## Feature

Feature는 Scene을 구성하는 기능성 UI 단위입니다.

```
BuildStructureBlock
BuildStructureGrid
BuildAIBlock
BuildVisualGallery
ProjectsNavigatorList
ProjectsNavigatorMonitor
ProjectsClosingStatement
```

Feature는 다음 역할을 담당합니다.

- 반복되는 UI 구조 분리
- props 기반 렌더링
- 사용자 interaction 처리
- Scene의 JSX 복잡도 축소
- 기능 단위의 스타일과 표현 관리

세부 카드나 목록, 모니터 미리보기처럼 실제 UI 조각을 변경하려면 Feature를 확인하면 됩니다.

---

## 계층별 변경 기준

```
전체 스크롤 챕터를 변경한다
→ Stage

한 장면의 화면 구성과 정보 위계를 변경한다
→ Scene

장면 안의 세부 UI나 interaction을 변경한다
→ Feature
```

컴포넌트 크기를 기준으로 자의적으로 나누는 대신, 각 계층이 답해야 하는 질문을 정했습니다.

---

# 5. 화면 구조와 애니메이션 실행 구조를 분리했습니다

스크롤 포트폴리오에서는 화면 컴포넌트와 애니메이션 코드가 쉽게 강하게 결합될 수 있습니다.

예를 들어 하나의 Scene 안에 다음 코드가 모두 들어갈 수 있습니다.

```
JSX 구성
DOM selector
GSAP Timeline
ScrollTrigger 등록
cleanup
```

이 경우 화면 구조를 변경할 때 애니메이션 실행 코드까지 함께 확인해야 하고, 스크롤 구간을 수정하려면 JSX 내부까지 들어가야 합니다.

그래서 화면 구조와 애니메이션 실행 구조를 서로 다른 책임으로 나눴습니다.

```
Stage Component
→ Stage root와 Scene 구성

Scene
→ 시각적 화면 구성

Feature
→ 기능성 UI 구성

Scene DOM Helper
→ Animation이 사용할 세부 DOM 수집

Animation Controller
→ GSAP Timeline과 실제 움직임 정의

Stage Hook
→ ScrollTrigger와 Controller 연결
```

전체 흐름은 다음과 같습니다.

```
Stage
└─ Scene
   └─ Feature

Stage Hook
├─ Stage Elements
├─ Animation Controller
└─ ScrollTrigger

Animation
└─ GSAP Timeline
```

화면을 구성하는 코드와 화면을 움직이는 코드는 연결돼 있지만, 같은 책임을 가지지는 않습니다.

따라서 Scene은 ScrollTrigger를 직접 만들지 않고, Animation은 React 렌더링이나 콘텐츠 데이터를 담당하지 않도록 제한했습니다.

---

# 6. DOM 탐색도 사용하는 계층에 따라 나눴습니다

모든 selector를 하나의 전역 파일에 모으지는 않았습니다.

selector가 어떤 계층에서 사용되는지를 기준으로 분리했습니다.

## Stage selector

ScrollTrigger의 기준이 되는 큰 구간을 찾습니다.

```tsx
export const BUILD_STAGE_SELECTORS = {
  intro: ".js-build-intro",
  introProof: ".js-build-intro-proof",
  structure: ".js-build-structure",
  ai: ".js-build-ai",
  visual: ".js-build-visual",
} as const;
```

Stage Hook은 다음 정도의 큰 구간만 알면 됩니다.

```
Intro
Structure
AI
Visual
```

## Scene selector

실제 Animation이 움직일 세부 요소를 찾습니다.

```tsx
export const BUILD_AI_ANIMATION_SELECTORS = {
  header: ".js-build-ai-header",
  grid: ".js-build-ai-grid",
  card: ".js-build-ai-card",
  title: ".js-build-ai-title",
} as const;
```

Scene 내부의 제목, 카드, 아이콘과 같은 마크업 구조는 해당 Scene의 DOM Helper가 알고 있습니다.

```
Stage selector
→ ScrollTrigger 기준이 되는 큰 영역

Scene selector
→ 실제 GSAP가 움직이는 세부 요소
```

모든 selector를 Stage constants에 모으면 Stage Hook이 Scene 내부의 마크업까지 알게 됩니다.

이 경우 카드나 제목 구조가 바뀔 때 상위 Stage 코드도 영향을 받습니다.

selector의 범위를 사용하는 계층으로 제한하면서, Scene 내부의 변경이 Stage 스크롤 흐름까지 퍼지지 않도록 했습니다.

---

# 7. 스타일 class와 Animation selector를 분리했습니다

화면 스타일과 JavaScript DOM 탐색에 같은 class를 사용하면 스타일 구조를 변경했을 때 Animation selector가 함께 깨질 수 있습니다.

그래서 역할을 구분했습니다.

```tsx
<section
  className="
    build-intro-scene
    js-build-intro
  "
>
```

```
build-intro-scene
→ SCSS 스타일을 위한 class

js-build-intro
→ JavaScript가 DOM을 찾기 위한 class
```

스타일 class는 BEM 기반으로 작성하고, `.js-*` class는 Animation target을 찾는 용도로만 사용했습니다.

```
스타일 변경
→ BEM class 수정

Animation 대상 변경
→ js-* selector 수정
```

화면 스타일과 Animation 연결 지점이 같은 문자열에 의존하지 않도록 분리한 것입니다.

Stage root는 이미 React ref로 직접 참조할 수 있으므로 별도의 `.js-*` class를 붙이지 않았습니다.

```tsx
<section ref={stageRef}>
```

반면 Stage 내부에서 `querySelector`로 찾아야 하는 요소에만 `.js-*` class를 사용했습니다.

```
Stage root
→ React ref

Stage 내부 Animation target
→ js-* class
```

# 8. 콘텐츠 데이터도 컴포넌트에서 분리했습니다

Build 영역에는 반복되는 카드와 설명이 많고, Projects 영역에는 프로젝트 목록과 상세 정보가 존재합니다.

이 데이터를 컴포넌트 내부에 직접 작성하면 JSX가 화면 구조와 콘텐츠 내용을 동시에 담당하게 됩니다.

```tsx
const items = [
  {
    title: "...",
    description: "...",
  },
];
```

그래서 긴 텍스트와 반복 렌더링 데이터는 도메인별 `data` 폴더로 분리했습니다.

```
data/
├─ build/
│  ├─ intro/
│  └─ experience/
│     ├─ buildStructureItems.ts
│     ├─ buildAIItems.ts
│     └─ buildVisualItems.ts
│
└─ projects/
   └─ projectItems.ts
```

컴포넌트는 전달받은 데이터를 화면에 표현하는 역할에 집중합니다.

```
내용을 변경한다
→ data

화면 구조를 변경한다
→ Scene 또는 Feature

움직임을 변경한다
→ Animation
```

콘텐츠 수정과 UI 구조 수정이 서로 다른 파일에서 이뤄지도록 변경 이유를 분리했습니다.

---

# 9. 스타일과 이미지도 도메인 경계를 따르도록 했습니다

컴포넌트만 Build와 Projects로 나누고 스타일이나 이미지가 기존 Capability 경로에 남아 있으면 구조가 절반만 분리된 상태가 됩니다.

그래서 SCSS namespace와 이미지 경로도 같은 도메인 경계를 따르도록 정리했습니다.

## Style

```
styles/features/
├─ build/
│  ├─ intro/
│  └─ experience/
│     ├─ structure/
│     ├─ ai/
│     └─ visual/
│
└─ projects/
   ├─ navigator/
   ├─ detail/
   └─ closing/
```

class namespace도 화면의 도메인이 드러나도록 구성했습니다.

```
build-intro-*
build-experience-*
projects-navigator-*
project-detail-*
projects-closing-*
```

## Assets

이미지 경로 Helper도 분리했습니다.

```
assets/
├─ buildImages.ts
└─ projectsImages.ts
```

정적 이미지 경로 역시 도메인에 맞게 변경했습니다.

```
public/images/
├─ build/
│  └─ visual/
│
└─ projects/
   ├─ washer/
   ├─ nova/
   ├─ hyoit/
   └─ portfolio/
```

이를 통해 `Capability`라는 기존 이름이 컴포넌트에서만 사라지고 다른 영역에 남아 있지 않도록 했습니다.

하나의 도메인을 변경할 때 컴포넌트, 스타일, 데이터, Animation, 이미지 경로가 같은 이름 아래 연결되도록 만든 것입니다.

---

# 10. 공통 코드와 도메인 코드를 구분했습니다

모든 코드를 Build와 Projects 안에 넣지는 않았습니다.

여러 도메인에서 실제로 같은 책임을 가지는 코드는 `shared`, `lib`, `providers` 영역에 두었습니다.

## shared

여러 화면에서 공통으로 사용하는 UI나 시스템 컴포넌트를 관리합니다.

```
Header
Button
Modal
GradientText
```

## lib

특정 화면에 속하지 않는 전역 유틸리티를 관리합니다.

```
GSAP plugin 등록
ScrollTrigger 생성 Helper
ScrollTrigger refresh
공통 progress 함수
```

## providers

앱 전체의 실행 환경을 관리합니다.

```
SmoothScrollProvider
Lenis 초기화
GSAP ticker와 Lenis 동기화
전역 스크롤 update
```

다음 질문을 기준으로 위치를 판단했습니다.

```
Build를 제거해도 이 코드가 필요한가?
Projects를 제거해도 이 코드가 필요한가?
여러 도메인에서 같은 의미로 사용되는가?
```

특정 화면의 맥락을 알아야 하는 코드는 해당 도메인에 남기고, 화면과 관계없이 같은 역할을 하는 코드만 공통 영역으로 이동했습니다.

단순히 두 곳에서 사용된다는 이유만으로 모든 코드를 전역 공통 폴더로 올리지는 않았습니다.

---

# 11. 폴더 구조가 변경 위치를 안내하도록 했습니다

리팩토링 이후에는 변경 목적에 따라 확인해야 할 위치를 예측할 수 있습니다.

| 변경하려는 내용             | 확인할 위치               |
| --------------------------- | ------------------------- |
| 전체 스크롤 챕터 구성       | `components/stages`       |
| 한 장면의 JSX와 정보 위계   | `components/scenes`       |
| 세부 UI와 interaction       | `components/features`     |
| Animation 대상 DOM          | `components/scenes/*/dom` |
| GSAP Timeline과 모션        | `animations`              |
| 반복 콘텐츠와 프로젝트 정보 | `data`                    |
| 도메인별 스타일             | `styles/features`         |
| 이미지 경로 규칙            | `assets`                  |
| 정적 이미지 파일            | `public/images`           |
| 프로젝트 상세 라우팅        | `app/projects/[id]`       |
| 전역 GSAP·스크롤 유틸       | `lib`, `providers`        |

폴더 구조가 단순한 저장 위치가 아니라, 코드를 수정할 때의 탐색 경로 역할을 하도록 설계했습니다.

---

# 12. 리팩토링 이후 무엇이 달라졌는가

## 화면의 의미가 코드에 드러나게 됐습니다

```
Build
→ 화면을 설계하고 구현하는 방식

Projects
→ 완성한 프로젝트 결과물
```

기존 `Capability`라는 넓은 이름 대신, 각 영역이 사용자에게 전달하는 내용을 코드에서도 확인할 수 있게 됐습니다.

## 변경 범위를 예측할 수 있게 됐습니다

Build의 AI 카드 내용을 변경하려면 Build Data와 Feature를 확인하면 됩니다.

Projects의 미리보기 전환을 변경하려면 Projects Navigator와 Animation을 확인하면 됩니다.

관련 없는 영역까지 함께 탐색할 필요가 줄었습니다.

## 도메인 경계가 프로젝트 전체에서 일관돼졌습니다

도메인 분리를 컴포넌트에서 끝내지 않고 다음 영역에 동일하게 반영했습니다.

```
Component
Animation
Data
Style
Asset
Image
Route
```

같은 기능과 함께 변경되는 파일들이 같은 도메인 이름을 사용하게 됐습니다.

## 화면 구조와 실행 구조가 분리됐습니다

```
화면의 계층
→ Stage → Scene → Feature

애니메이션 실행
→ DOM Helper → Animation Controller → Stage Hook
```

화면을 구성하는 책임과 화면을 움직이는 책임을 서로 다른 구조로 표현했습니다.

## 폴더 깊이보다 책임의 경계를 우선했습니다

모든 파일을 잘게 쪼개는 것을 목표로 하지 않았습니다.

다음 기준으로 분리했습니다.

```
서로 다른 이유로 변경되는가?
상위 코드가 하위 구현을 지나치게 많이 알고 있는가?
사용자가 이해하는 화면의 단위와 일치하는가?
특정 도메인을 제거해도 독립적으로 정리할 수 있는가?
```

같은 책임을 가진 코드는 함께 두고, 다른 이유로 변경되는 코드는 분리했습니다.

---

# 마무리

이번 리팩토링에서 가장 중요했던 것은 폴더를 보기 좋게 정리하는 일이 아니었습니다.

사용자가 화면을 이해하는 구조와 코드가 변경되는 구조를 일치시키는 일이었습니다.

```
페이지의 큰 흐름
→ Stage

Stage 안의 시각적 장면
→ Scene

장면을 구성하는 기능성 UI
→ Feature

실제 움직임
→ Animation

움직일 DOM 탐색
→ Scene DOM Helper

스크롤과 Animation 연결
→ Stage Hook
```

또한 기존 `Capability`가 함께 담당하던 두 가지 의미를 분리했습니다.

```
어떻게 만드는가
→ Build

무엇을 만들었는가
→ Projects
```

이 경계를 컴포넌트에만 적용하지 않고 Animation, Data, Style, Asset, Image, Route까지 일관되게 반영했습니다.

이번 작업을 통해 폴더 구조는 단순히 파일을 저장하는 위치가 아니라는 점을 확인했습니다.

```
코드를 어디서 찾아야 하는지 알려주는가?
무엇과 함께 변경되는지 보여주는가?
각 파일의 책임을 이름만으로 예상할 수 있는가?
새로운 기능이 추가될 위치를 예측할 수 있는가?
```

이 기준을 바탕으로 기능이 늘어나더라도 관련 없는 영역까지 수정 범위가 퍼지지 않고, 화면의 의미와 코드의 책임을 함께 이해할 수 있는 구조를 만들었습니다.
