# 이력서와 포트폴리오의 문제점 분석

이 문서는 LinkedIn을 통해 받은 여러 현업 개발자의 피드백을 종합해 현재 이력서와 포트폴리오의 문제점을 정리한 기록이다.

개인의 의견을 그대로 정답으로 받아들이기보다, 여러 피드백에서 반복적으로 나타난 공통점을 중심적으로 분석했다.

## 1. 이력서가 지나치게 압축되어 있어 경험의 깊이가 보이지 않음

현재 이력서는 짧고 깔끔하지만, 프로젝트에서 실제로 했던 고민과 문제 해결 과정이 많이 생략되어 있다.

이력서에서는 다음 내용은 확인할 수 있었다.

- 어떤 프로젝트를 진행했는지
- 어떤 기술을 사용했는지
- 어떤 기능을 구현했는지

하지만 다음 내용은 충분히 드러나지 않는다.

- 왜 해당 기술을 선택했는지
- 어떤 문제가 발생했는지
- 어떤 기준으로 해결 방법을 선택했는지
- 결과적으로 무엇이 달라졌는지
  이 때문에 실제 경험보다 이력서가 빈약해 보일 수 있으며, 채용 담당자가 포트폴리오까지 확인할 동기가 약해질 수 있다.

> **피드백 출처 :** 다수의 프론트엔드 현업 개발자, 채용 평가 경험이 있는 개발자

### 피드백 내용

- 이력서가 너무 함축되어 있어, 공들인 포트폴리오까지 도달하기 어려워 보인다고 지적
- 실무 경험보다 프로젝트 중심인데 이력서 분량이 적어, 경험이 빈약해 보일 수 있다고 평가
- 이력서가 지나치게 요약되어 있어 포트폴리오와 합치는 편이 나을 수 있다고 언급
- 포트폴리오에는 고민이 있지만 첫인상인 이력서에는 충분히 담겨 있지 않다고 지적
- 평가자는 이력서의 절반만 본다고 가정하고 가장 강한 경험을 앞에 보여줘야 한다고 조언
- 프로젝트 경험이 무엇을 했는지만 설명하고 있다고 평가

## 2. 프로젝트 설명이 '무엇을 했다'에서 끝남

가장 많이 반복된 피드백

현재 프로젝트 설명은 다음과 같은 형식에 가깝다.

- FSD 구조 설계
- TanStack Query를 활용한 서버 상태 관리
- GSAP 기반 인터랙션 구현
- 관리자 페이지 개발
- 반응형 UI 구축

이 문장들은 작업 내용을 알려주지만, 채용 담당자가 다음 질문에 답을 얻기는 어렵다.

- 왜 이 작업이 필요했는가
- 기존엔 어떤 문제가 있었는가
- 이 기술을 사용해서 무엇이 좋아졌는가
- 사용자나 팀에 어떤 영향이 있었는가
- 성공인지 실패인지 어떻게 판단했는가

즉, 구현 사실은 있지만 **성과와 의미가 약하다.**

프로젝트 설명에는 다음 흐름이 필요하다

**문제 → 판단 → 해결 → 결과**

> **피드백 출처:** 현업 개발자 다수의 공통 의견

### 피드백 내용

- 무엇을 했는지보다 왜 했고, 어떤 개선과 영향을 만들었는지가 보여야 한다고 지적
- `설계`, `구성`, `구축` 같은 표현이 질문이나 호기심을 만들지 못한다고 평가
- 문제 정의, 접근, 해결, 개선 과정이 부족하다고 언급
- 프로젝트에서 무엇을 배웠고 어떤 문제를 해결했는지가 드러나지 않는다고 지적
- 성공, 실패 여부, 원인, 구현 이유가 더 흥미로운 내용이라고 설명
- "무엇을 했다"는 많지만 "그래서 어떻게 좋아졌는가"가 약하다고 평가
- XYZ 또는 CAR 방식으로 방법 & 성과 & 측정치를 함께 써야한다고 제안
- What과 How는 있지만 Why가 부족하다고 지적
- 기능 나열보다 상황·적용 기술·결과를 중심으로 일관되게 써야 한다고 조언
- `문제 → 해결 방식 → 결과 구조`로 바꿔야 한다고 제안

## 3. 기술 선택의 이유와 비교 과정이 부족함

현재는 어떤 기술을 사용했는지는 보이지만, 왜 그 기술이어야 했는지는 충분히 설명되지 않는다.

예를 들어, 다음과 같은 질문이 남는다.

- 왜 FSD 였는가
- 왜 TanStack Query 였는가
- 왜 Zustand 였는가
- 왜 GSAP와 Lenis 였는가
- 왜 Next.js 였는가
- 다른 대안과 무엇을 비교했는가
- 프로젝트 규모에 과한 선택은 아니었는가
- 다시 해도 같은 선택을 할 것인가.

이 부분이 부족하면 기술을 깊게 이해하고 선택한 것이 아니라, 유명한 기술을 가져다 쓴 것처럼 보일 수 있다.

> **피드백 출처:** 프론트엔드 개발자 및 기술 멘토 피드백

### 피드백 내용

- What & How 보다, Why가 관찰되지 않았다고 평가
- FSD 정의만 외우지 말고, 회사가 왜 그 구조를 선택했는지까지 생각해야 한다고 조언
- Washer에서 FSD를 쓴 이유와 무엇이 나아졌는지를 이력서에 넣어야 한다고 설명
- 특정 아키텍처를 도입한 이유와 구체적인 이점을 설명하지 못하면 역효과가 날 수 있다고 지적
- 왜 구현하기로 결정했는지, 그 결정이 옳았는지, 무엇을 배웠는지가 중요하다고 평가
- 여러 기술을 비교하고 왜 선택했는지를 보여주면 좋겠다고 저언
- 면접관이 "왜 FSD를 선택했나요?"라고 질문할 수 있도록 써야 한다고 설명

## 4. 프로젝트 결과와 정량적 근거가 부족함

현재 자료에는 구현 내용은 있지만, 프로젝트의 규모와 결과를 확인할 수 있는 숫자가 충분하지 않다.

예를 들면 다음과 같은 정보가 더 필요하다.

- 실제 사용자 수
- 활성 사용자 수
- 구현한 화면 수
- API 연동 수
- 운영 기간
- 팀 규모
- 담당 버무이
- 오류나 문의 감소
- 로딩 속도 개선
- 사용자 테스트 결과
- 배포 횟수

다만 실제 측정하지 않은 퍼센트나 성과를 만들어 쓰면 안 된다.

> **피드백 출처:** 채용 경험이 있는 개발자, 현업 개발자 다수

### 피드백 내용

- 프로젝트 성과를 숫자로 표현하면 더 설득력 있다고 조언
- 사용자 수, MAU·DAU, 성능 개선, 사용자 테스트 결과가 추가되면 좋겠다고 평가
- XYZ 방식으로 성과와 측정치를 같이 쓰라고 제안
- 큰 매출 수치가 없어도 화면 수, 역할, 오류, 개선 전후를 구체적으로 쓰라고 조언
- 구현이 실제로 쓸모 있었는지 논리적으로 설명하려면 결과가 필요하다고 지적
- 사용자나 프로젝트에 어떤 긍정적 임팩트를 줬는지 명시해야 한다고 언급
- 기여 이후 결과가 어떻게 되었는지를 추가해야 한다고 평가

## 5. Washer의 실사용·운영 경험을 충분히 활용하지 못함

Washer는 현재 자료에서 가장 강한 프로젝트 중 하나이다.
강한 이유는 단순히 기술이 많아서가 아니라 다음 조건을 갖고 있기 때문이다.

- 실제 학교에서 사용하는 서비스
- 학생과 관리자가 존재함
- 운영 중 문제가 발생함
- 백엔드와 협업함
- 인증서, 캐시, 상태 관리 문제를 경험함
- 실제 사용자 흐름을 고려함

그런데 현재는 이 프로젝트가 일반적인 관리자 페이지 갭라처럼 보일 가능성이 있다.

실제 사용자 수, 운영 과정, 발생한 문제와 해결 결과를 더 전명에 배치해야 한다.

> **피드백 출처:** 스타트업 개발자, 채용 평가 경험이 있는 개발자, 고절 취업 경험자

### 피드백 내용

- 전교생이 사용하는 실제 서비스인데 단순히 "해봤다" 로 끝난다고 지적
- "전교생이 사용하는 세탁기 서비스"는 매우 신선하고 질문을 유도할 소재라고 평가
- 실제 사용자와 운영 경험이 있는 Washer를 더 앞에 배치하라고 조언
- 전교생 200명 이상 실사용 서비스 경험은 좋은 자산이라고 평가
- 실제 운영 경험은 학력 장벽을 보완할 객관적인 근거가 될 수 있다고 언급
- 학교에서 실제로 운영하며 마주한 문제를 스토리로 풀면 좋은 셀링 포인트가 된다고 조언
- 사용자 수와 운영 성과를 구체적으로 표현하라고 제안

## 6. 포트폴리오가 UX·인터랙션 중심으로 보이고 엔지니어링 깊이는 약하게 보임

현재 포트폴리오의 가장 분명한 강점은 다음이다.

- 시각적 완성도
- 스크롤 인터랙션
- 애니메이션
- 스토리텔링
- UI와 UX에 대한 관심
  하지만 이 장점이 너무 앞에 나오면서, 일부 평가자는 다음처럼 볼 수 있다.

> 퍼블리싱과 화면 구현에는 강하지만, 상태 관리, 데이터, 아키텍처, 성능 같은 프론트엔드 엔지니어링은 얼마나 깊을까?

즉, 장점이 오히려 포지셔닝을 좁히고 있다.

### 피드백 내용

- 포트폴리오가 프론트엔드 개발자보다 퍼블리셔 성격으로 보일 수 있다고 평가
- 시각적인 레퍼런스는 잘 보이지만 엔지니어링 문제 해결 과정이 더 필요하다고 조언
- 단순히 화면을 예쁘게 만드는 것을 넘어 인터랙션의 구현 원리와 트러블 슈팅을 보여줘야 한다고 언급
- 설계했다고 적혀 있지만 실제 구조를 확인할 수 없다고 지적
- 기능 동작 과정을 시퀸스 다이어그램으로 보여주면 좋겠다고 조언
- UX뿐 아니라, AX 관점까지 확장하면 좋겠다고 제안

## 7. 설계와 아키텍처를 글로만 설명하고 시각 자료가 부족함

현재 포트폴리오에서 `설계했다`, `구조화했다`, `분리했다` 는 표현은 많지만 실제 구조를 한눈에 확인하기는 어렵다.

채용 담당자가 긴 글을 읽지 않아도 다음을 볼 수 있어야 한다.

- API 요청 흐름
- 인증 흐름
- QueryKey 구조
- 서버와 클라이언트의 요청 경로
- 상태 변화
- 부모 & 자녀 앱 구조
- FSD 레이어 구성

글만으로 설명하면 실제로 설계한 구조인지, 단순히 용어를 사용한 것인지 판단하기 어렵다.

> **피드백 출처:** 백엔드 및 프론트엔드 현업 개발자 피드백

### 피드백 내용

- 구조도와 플로우차트가 없다고 직접 지적
- 주요 기능의 동작 과정을 시퀸스 다이어그램으로 표현하라고 제안
- 데이터 전달과 컴포넌트 결합도를 구조적을 다시 고민하라고 조언
- 면접관이 구체적인 흘므을 이해할 수 있게 작성해야 한다고 설명

## 8. 트러블슈팅 설명의 흐름과 정확성이 부족

특히 Washer의 자체 서명 인증서 문제는 강한 경험이 될 수 있지만, 현재 설명에는 다음 문제가 있다.

- 왜 특정 시도를 했는지 부족함
- CORS와 TLS 문제가 혼재함
- 인증서 문제와 미들웨어 접근 제어가 섞여 있음
- 요청 흐름 분석의 근거가 부족함
- API 프록시, 환경 변수, rewrite, 보안 구조를 깊게 검토해야 한다고 설명
- 실제 운영 중 발생한 문제와 해결 과정을 보강해야 한다고 조언
- 초기 가설, 비교, 선택 이유, 결과를 기록해야 한다고 설명

## 9. 모바일과 인터랙션 완성도에 실제 문제가 있음

포트폴리오가 인터랙션을 강점으로 내세우기 때문에, 모바일 오류는 일반적인 사이트보다 더 큰 감점 요소이다.

직접 지적된 문제는 다음과 같다.

- 모바일 drawer 배경 누락
- 캐러셀 구간에서 세로 스크롤이 막힘
- 일부 모바일 화면 깨짐
- 헤더 텍스트 가독성 저하
- 요소와 텍스트가 겹침

이는 단순한 작은 버그가 아니라, 본인이 내세우는 `디테일`, `UX`, `인터렉션` 이라는 강점과 충돌한다.

새로운 애니메이션을 추가하기보다 기존 인터랙션을 안정적으로 수정하는 것이 우선이다.

> **피드백 출처:** 모바일로 포트폴리오를 검토한 프론트엔드 개발자 다수

### 피드백 내용

- 모바일 drawer 배경, 캐러셀 스크롤, 반응형 깨짐을 직접 지적
- 투명한 헤더 때문에 다른 요소와 겹처 텍스트가 보이지 않는 문제를 지적
- 인터랙션과 화면 구현 중심의 포트폴리오일수록 기술적 완성도가 필요하다고 평가
- 인터랙션의 부드러운 구현과 트러블슈팅을 기록해야 한다고 조언

## 10. 수상 경력과 객관적인 강점이 너무 뒤에 있음

현재 수상 경력은 충분히 강한 요소인데, 이력서 하단에 배치되어 첫인상에서 잘 보이지 않는다.

현재 가진 강한 근거는 다음과 같다.

- 과학기술정보통신부 장관상
- AppJam 우수상
- 실사용 서비스 운영
- 팀 리드 경험
- 꾸준한 GitHub 활동

이런 요소는 개발 철학이나 추상적인 슬로건보다 먼저 보여줄 가치가 있다.

> **피드백 출처:** 채용 평가 경험자, 스타트업 개발자, 고졸 취업 경험자

### 피드백 내용

- 공신력 있는 수상과 외부 인정이 학력 장벽을 보완하는 후킹 요소라고 평가
- 수상 실적을 상단 소개에 녹여야 한다고 조언
- 장관상, 실사용 서비스, 커밋 기록을 슬로건 아래 바로 넣으라고 제안
- 수상과 대외 활동을 첫 페이지에 배치하라고 조언
- 철학보다 결과와 근거를 앞에 두라고 평가

## 11. 오탈자와 표기 불일치가 디테일에 대한 신뢰를 떨어트림

현재 자료에서는 다음과 같은 문제들이 확인되었다.

- `광주기술정보통신부` 표기
- `Github`
- `FrontEnd Develop`
- `FrontEnd Developer`
- `React Query`와 `TanStack Query` 혼용
- `인터렉션`
- `드러나더록`
- 기타 영문 대소문자와 표현 혼용

사용자가 직접 디테일을 중요하게 생각한다고 말하고 있기 때문에, 작은 오류가 더 크게 보인다.

> **피드백 출처:** 다수의 현업 개발자

### 피드백 내용

- GitHub, Frontend 관련 표기 혼용 지적
- React Query를 TanStack Query로 통일하라고 조언
- 기관명과 유사 오타를 전부 수정하라고 지적
- 장관상 수상 기관명이 잘못되어 있다고 지적
- `드러나더록`, `인터렉션` 오타를 직접 지적

## 12. 링크와 정보가 많지만 우선순위가 명확하지 않음

상단에 여러 링크가 있고, 포트폴리오 내부에서도 상세 링크가 많아 사용자가 무엇을 먼저 봐야 할지 모호할 수 있다.

모든 링크를 확인하는 평가자는 많지 않다.

따라서 다음이 필요하다.

- 핵심 링크 1~2개만 상단 배치
- 대표 프로젝트를 먼저 보여주기
- 상세 글은 필요한 위치에만 연결
- 이력서만 읽어도 핵심 판단이 가능하게 만들기

> **피드백 출처:** 현업 개발자 및 이력서 리뷰 경험자

### 피드백 내용

- 상단 링크 3개 중 하나를 보기도 쉽지 않다고 지적
- 보여주고 싶은 프로젝트 경험에만 선별적으로 링크를 걸라고 조언
- 이력서와 포트폴리오를 나누면 각각 빈약하게 보일 수 있다고 평가
- 이력서만으로도 포트폴리오의 핵심 내용이 보여야 한다고 조언

## 13. 현재 포지셔닝이 너무 좁거나 추상적일 수 있음

현재 브랜딩은 인터랙션, 디테일, UX에 강하게 맞춰져 있다.

이런 포지셔닝은 관련 회사에는 매력적이지만, 다음 회사에는 제한적으로 보일 수 있다.

- B2B SaaS
- 관리자 서비스
- 데이터 중심 서비스
- 복잡한 상태 관리가 중요한 조직
- 안정성과 비즈니스 로직을 더 보는 팀

반대로 너무 추상적인 개발 철학도 강한 첫인상을 만들기 어렵다.

UX 강점을 유지하면서 다음과 같이 기술 영역을 확장해 표현할 필요가 있다.

- "사용자 경험과 데이터 흐름을 함께 설계하는 프론트엔드 개발자"
- 인터랙션의 디테일부터 상태와 API 구조까지 고민하는 프론트엔드 개발자

> **피드백 출처:** 채용 경험이 있는 프론트엔드 개발자, 커리어 멘토

### 피드백 내용

- 특정 A형 개발자로 자신을 규정하면 다른 조직에서 후보에서 제외될 수 있다고 설명
- 신입이나 철학이나 좌우명만으로 시선을 붙잡기는 어렵다고 평가
- 사용할 수 있는 도구는 보이지만 본인의 전문성이 무엇인지 빠져 있다고 지적
- 내가 하고 싶은 이야기보다 회사가 관심 가질 소재를 전면에 보여줘야 한다고 조언
- 회사가 필요로 하는 역량을 먼저 파악하고 이력서에 녹이라고 조언

## 14. AI 활용 경험이 보이지 않거나 너무 단순하게 표현될 가능성이 있음

AI 를 실제로 많이 사용하고 있지만, 현재 자료만 보면 다음이 충분히 드러나지 않을 수 있다.

- 어떤 작업에 사용했는지
- AI 결과를 어떻게 검증했는지
- 어떤 제안을 거절했는지
- 기존 개발 방식과 무엇이 달라졌는지
- AI API를 제품에 어떻게 연결했는지
- AI 결과를 사용자에게 어떤 UX로 전달했는지
  단순히 `ChatGPT`, `Claude` 를 사용했다고 적는 것으로는 부족하다.

AI 사용 자체보다 **판단, 검증, 사용자 문제 해결** 을 보여줘야 한다.

> **피드백 출처:** AI·프론트엔드 분야 현업 개발자 다수

### 피드백 내용

- AI를 어떻게 활용했는지가 포트폴리오에 담기면 좋겠다고 조언
- 기술 목록보다 AI를 활용해 도메인 문제를 해결한 경험을 강조하라고 평가
- AI 시대에 맞게 활용 범위를 넓히라고 조언
- AI Agent와 프롬프트를 통해 개발 효율을 높인 사례를 준비하라고 조언
- AI 사용 자체보다 기존 개발과 무엇이 달라졌는지를 보여주라고 조언
- 조금이라도 AI를 사용한 경험이 있다면 부각하라고 제안

## 15. 회사별 맞춤성이 부족함

현재 이력서는 고정된 버전으로 다양한 회사에 제출되는 성격이 강하다.

그러나 회사마다 원하는 프론트엔드 개발자는 다르다.

- **작은 스타트업 :** 실행력, 다양한 역할
- **B2B :** 데이터, 상태, 운영
- **UX 회사 :** 인터랙션, 접근성
- **모바일 회사 :** React Native와 모바일 흐름
- **규모가 큰 회사 :** 기본기, 협업, 안정성

프로젝트 순서와 강조점은 회사에 따라 달라져야 한다.

> **피드백 출처:** 스타트업 재직 개발자, 채용 경험자, 커리어 멘토

### 피드백 내용

- JD를 분석하고 이력서 강조점을 조정하라고 조언
- 회사와 팀으 규모에 따라 기대치가 다르며, 회사 유형별로 묶어 준비하라고 제안
- 회사 사업과 기술 스택을 연결해 면접을 준비하라고 조언
- 회사가 필요로 하는 것을 먼저 파악하라고 지적
- 지원한 조직이 명확한지에 따라 포지셔닝 전략을 바꿔야 한다고 설명

## 종합 진단

현재 자료의 문제는 다음 한 문장으로 정리 할 수 있다.

> 프로젝트와 경험은 신입 기준으로 충분히 경쟁력이 있지만,
>
> 이력서에서는 지나치게 압축되어 있고,
>
> 포트폴리오에서는 UX와 구현 결과가 앞서 있어,
>
> 기술적 판단, 문제, 해결, 운영 경험, 성과가 실제보다 약하게 보인다.

### 긍정적인 인상

- 어린 나이에 프로젝트 경험이 많음
- 인터랙션과 시각적 표현에 관심이 많음
- 실제 서비스 경험이 있음
- 수상 경력이 좋음
- 꾸준히 개발함
- 기록과 포트폴리오에 공을 들임

### 남을 수 있는 의문

- 왜 이 기술을 선택했는가
- 실제로 어떤 문제를 해결햇는가
- 사용 후 무엇이 달라졌는가
- 상태와 데이터 구조를 얼마나 깊게 이해하는가
- 라이브러리 없이 원리를 설명할 수 있는가
- 실제 운영 과정에서 무엇을 배웠는가
- UI 구현 외에 프론트엔드 엔지니어링 깊이는 어느 정도인가
- 모바일과 예외 환경까지 충분히 검수했는가
