# 포트폴리오 사용자 행동 분석 도구 선택

## 배경

현재 포트폴리오는 인터랙션과 스크롤 스토리텔링을 중심으로 구성되어 있다.

하지만 사용자가 실제로 다음과 같이 행동하는지는 확인할 수 없었다.

- 프로젝트 섹션까지 도달하는지
- 어떤 프로젝트를 가장 많이 확인하는지
- 이력서와 GitHub 링크를 클릭하는지
- 특정 인터랙션 구간에서 이탈하는지
- 모바일 환경에서 스크롤이나 캐러셀 사용에 어려움을 겪는지

기존에는 디자인과 인터랙션을 주관적으로 판단했다면, 이후에는 실제 사용자 행동 데이터를 기반으로 포트폴리오를 개선하기 위해 분석 도구 도입을 검토했다.

---

## 검토한 도구

### Lighthouse

웹페이지의 기술적인 품질을 측정하는 도구다.

측정 가능한 항목은 다음과 같다.

- Performance
- Accessibility
- Best Practices
- SEO
- LCP
- CLS
- TBT

Lighthouse는 사용자 행동을 분석하는 도구는 아니지만, 리팩터링 전후의 성능과 접근성 변화를 비교하는 데 적합하다.

---

### PostHog

제품 분석과 개발 도구를 함께 제공하는 플랫폼이다.

주요 기능은 다음과 같다.

- 이벤트 분석
- 퍼널 분석
- 세션 리플레이
- 히트맵
- 기능 플래그
- 실험
- 에러 추적

사용자 행동 분석뿐 아니라 에러 추적과 기능 실험까지 한 도구에서 관리할 수 있다는 장점이 있다.

---

### Amplitude

사용자 행동과 제품 전환을 분석하는 플랫폼이다.

주요 기능은 다음과 같다.

- 이벤트 분석
- 퍼널 분석
- 사용자 경로 분석
- 세션 리플레이
- 히트맵
- 사용자 세그먼트 비교

사용자가 어떤 단계까지 이동했고, 어느 지점에서 이탈했는지 분석하는 데 강점이 있다.

---

## 비교

| 항목          | Lighthouse     | PostHog             | Amplitude             |
| ------------- | -------------- | ------------------- | --------------------- |
| 성능 측정     | 강함           | 제한적              | 제한적                |
| 접근성 측정   | 강함           | 없음                | 없음                  |
| 이벤트 분석   | 없음           | 지원                | 지원                  |
| 퍼널 분석     | 없음           | 지원                | 강함                  |
| 세션 리플레이 | 없음           | 지원                | 지원                  |
| 히트맵        | 없음           | 지원                | 지원                  |
| 에러 추적     | 없음           | 지원                | 제한적                |
| 주요 목적     | 기술 품질 측정 | 개발·제품 분석 통합 | 사용자 행동·전환 분석 |

## 최종 선택

포트폴리오에는 다음 조합을 적용하기로 했다.

> Lighthouse + Amplitude

### Lighthouse를 선택한 이유

포트폴리오의 이미지, 스크롤 애니메이션, GSAP 초기화 과정이 성능에 미치는 영향을 확인하고, 리팩터링 전후의 차이를 수치로 비교하기 위해 선택했다.

### Amplitude를 선택한 이유

현재 가장 확인하고 싶은 것은 다음과 같은 사용자 행동이다.

- 프로젝트 섹션 도달률
- 프로젝트 상세 클릭률
- 이력서와 GitHub 클릭률
- 연락 수단 클릭률
- 모바일과 데스크톱의 행동 차이
- 특정 섹션에서의 이탈

PostHog도 유사한 기능을 제공하지만, 현재 목적은 에러 추적이나 기능 플래그보다 사용자 행동과 퍼널 분석에 더 가깝다고 판단했다.

따라서 포트폴리오에서는 Amplitude를 우선 적용하고, 추후 에러 추적이나 기능 실험이 필요해질 경우 PostHog 또는 Sentry 도입을 별도로 검토하기로 했다.

---

## Washer Admin에 적용하지 않은 이유

Washer Admin은 포트폴리오와 달리 일반 방문자가 자유롭게 탐색하는 서비스가 아니다.

또한 관리자 서비스 특성상 다음과 같은 제약이 있다.

- 사용자 수가 적음
- 접근 권한이 제한됨
- 실제 운영 데이터 수집에 대한 동의가 필요함
- 방문 퍼널보다 업무 성공 여부가 더 중요함
- 행동 데이터를 수집해도 표본이 충분하지 않을 수 있음

따라서 Washer Admin에는 Amplitude를 억지로 적용하지 않기로 했다.

Washer Admin에서는 사용자 행동 분석보다 다음 항목이 더 적합하다고 판단했다.

- 프론트엔드 에러 추적
- API 오류 기록
- 관리자 업무 처리 시간
- 오류 및 문의 건수
- Sentry 기반 모니터링

## 추적할 이벤트

초기에는 이벤트를 과도하게 만들지 않고 핵심 행동만 수집한다.

```text
portfolio_viewed
project_section_viewed
project_clicked
resume_clicked
github_clicked
contact_clicked
```

## 분석할 퍼널

```
포트폴리오 방문
→ 프로젝트 섹션 도달
→ 프로젝트 상세 클릭
→ 이력서 또는 GitHub 클릭
→ 연락 수단 클릭
```

## 진행 계획

### 1. 현재 상태 기록

- 모바일 Lighthouse 측정
- 데스크톱 Lighthouse 측정
- 주요 성능 지표 기록
- 현재 화면과 프로젝트 순서 저장

### 2. Amplitude 적용

- 핵심 이벤트 정의
- 이벤트 수집 코드 추가
- 모바일과 데스크톱 환경 구분
- 개인정보가 수집되지 않도록 점검

### 3. 데이터 수집

- 일정 기간 사용자 행동 데이터 수집
- 프로젝트 섹션 도달률 확인
- 링크 클릭률 확인
- 세션 리플레이 및 이탈 구간 확인

### 4. 문제 선정

다음 중 가장 명확한 문제 하나를 선택한다.

- 프로젝트 섹션 도달률이 낮음
- 프로젝트 상세 클릭률이 낮음
- 모바일 특정 구간에서 이탈
- 이력서나 GitHub 링크 클릭률이 낮음
- 스크롤 애니메이션 구간에서 탐색이 멈춤

### 5. 개선

- 프로젝트 순서 변경
- 애니메이션 길이 축소
- CTA 문구 개선
- 상단 정보 구조 변경
- 모바일 캐러셀 개선
- 링크 수 축소

### 6. 재측정

개선 전과 동일하거나 유사한 조건에서 다시 측정한다.

## 기대 결과

단순히 분석 도구를 설치한 경험이 아니라 다음 과정을 만드는 것이 목표다.

> 측정 → 문제 발견 → 가설 수립 → 수정 → 재측정

최종적으로는 다음과 같은 형태로 이력서와 포트폴리오에 활용할 수 있다.

```
Amplitude 사용자 행동 데이터를 분석해 프로젝트 섹션의 낮은 도달률을 발견하고,
정보 위계와 인터랙션을 개선해 프로젝트 상세 클릭률을 높였다.
```

```
Lighthouse 분석을 기반으로 이미지와 애니메이션 초기화 구조를 개선해
모바일 성능 지표를 향상했다.
```

단, 실제 측정 결과가 확인된 이후에만 수치와 성과를 작성한다.

---

## 결론

포트폴리오에는 기술 품질 측정을 위한 Lighthouse와 사용자 행동 분석을 위한 Amplitude를 적용한다.

Washer Admin에는 제품 분석 도구를 억지로 적용하지 않고, 추후 실제 운영 환경에서 에러 추적과 업무 지표 측정이 필요할 경우 Sentry와 로그 기반 모니터링을 우선 검토한다.
